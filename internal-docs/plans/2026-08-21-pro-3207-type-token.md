# A non-class `type:` token declares cleanly and raises a bare TypeError

**Status: complete.**

**Ticket:** https://linear.app/teamshares/issue/PRO-3207/axn-a-non-class-type-token-declares-cleanly-and-raises-a-bare

## Problem

PRO-3165/PRO-3166 closed a defect in every `of:` bag position: a token that is not a Class/Module, not a
union of them, and not one of `:boolean`/`:uuid`/`:params` reaches `value.is_a?(token)` and raises a bare
`TypeError: class or module required` on every call, naming neither the field nor the option. A field's own
`type:` — the most common spelling, and the last one — was left open on purpose: it is not an `of:`
position, and its sugar routes were unaudited.

Measured at `5e309e17`: `expects :v, type: false` (or `5`, `"String"`, `:nonsense`, `[String, nil]`,
`{ klass: false }`) declares without complaint and fails **every** call with the bare `TypeError`, settling
as an exception outcome reported through `Axn.config.on_exception` as an internal error.

## Design

One guard, at the one seam already shared by every `type:` spelling: `Contract#_canonicalize_validator_options!`
(`lib/axn/core/contract.rb`), which applies `TypeValidator.apply_syntactic_sugar` and is reached by both
routes a `type:` can be declared through (`_parse_field_validations` for `expects`/`exposes`/subfields/
ambient subfields/block-form shape members; `ShapeDeclaration#_symbol_keyed_member_validations` for a raw
`shape:` member). `_reject_unsupported_type_klass!` composes exactly the machinery PRO-3166 already built
and extracted for reuse — `_declared_type_klass`, `_declared_type_tokens`, `_reject_unsupported_type_token!`
(the index-based union search), `_supported_type_token?`, `_declared_type_label` — with no fourth copy of
any of it.

Two decisions, both resolved in the guard as shipped:

1. **Emptiness is folded in, not deferred.** A bag's `klass:` defers "supplied but names nothing" to
   `_reject_unconstraining_of_bag!`, because a bag has two other ways to constrain (`of:`, `shape:`). A
   field's `type:` has none, so it is the bare-axis situation instead: `type: nil`, `type: []`,
   `type: { klass: [] }` and `type: { message: "…" }` all raise here, exactly as `_reject_unsupported_map_axis!`
   folds the same case into itself for a bare `keys:`/`values:` axis.
2. **`model:` gets a dedicated, narrower guard rather than reusing `type:`'s.** It has the identical hole in
   the identical field position (`ModelValidator` builds a `TypeValidator` and delegates), but not the same
   grammar: a model class is resolved by calling a finder method **on** it, never by asking a value `is_a?`
   of it, so a union or a `:boolean`/`:uuid`/`:params` pseudo-type has nothing to dispatch through.
   `_reject_unsupported_model_klass!` requires a single Class/Module (`case klass; when ::Module`) rather
   than reusing `_declared_type_tokens`/`_reject_unsupported_type_token!`'s union-aware search, which would
   have accepted a union that only fails later — see below.

The guard defers when `of:` is also declared on the same field: `_declared_of_container!` runs
unconditionally whenever `:of` is present and already holds `type:` to a strictly narrower rule (Array or
Hash only), naming the classes that are actually legal there. Firing first would prescribe the weaker fix
and cost the author a second edit — the same deferral `_reject_unsupported_of_klass!` makes to
`_inner_of_container!`.

**Round-1 Codex finding (CONFIRMED): the `shape:` deferral was unconditional on key presence, and that was
wrong.** `_derive_raw_shape_container!` only calls `_shape_compatible_type!` to DERIVE a container when the
raw shape's own `container:` is nil/absent; a shape supplying its own already-valid `container:`
(`expects :v, type: false, shape: { members: [], container: Hash }`) skips derivation entirely —
`_reject_non_class_container!` passes the explicit `Hash` through untouched, and `type:` itself is never
independently checked by anything. That declared cleanly and reached `value.is_a?(false)` on every call,
the exact defect this ticket exists to close. First fix: narrow the deferral to the one case still safe —
`_shape_container_already_settled?` true only when the shape's `container:` is present AND already a valid
Module. Verified by hand across every combination before re-requesting review.

**Round-2 Codex finding (CONFIRMED, and it invalidated round 1's fix): the narrowed predicate still read the
shape's `container:` a second time, independently of whatever `_derive_raw_shape_container!` reads later —
and a hostile `[]` that answers differently across the two reads defeats BOTH checks.** Reproduced with a
`Hash` subclass overriding `[]` to return `nil` on the first read of `:container` and `Hash` on the second:
on a raw shape MEMBER (`_symbol_keyed_member_validations`, which — unlike the field-level path — has no
prior snapshot pass forcing the shape into an axn-owned plain Hash before this guard runs), the guard's own
read saw `nil` (→ "not settled" → defer), while a later, independent read during the member's own recursive
shape walk saw `Hash` (→ container "already settled" from THAT read's perspective → no derivation → no
check) — `type: false` declared cleanly and reached `value.is_a?(false)` on every call again, on exactly
the shape this ticket exists to close.

This is a genuinely hostile object (a `Hash` subclass with a stateful `[]` — no ordinary developer writes
one for a plain options Hash), so on its own it would be a `[[feedback_hostile_classes_not_our_responsibility]]`
rebuttal. But the fix that actually closes it is *simpler* than the guard it replaces, not more defensive,
so there was no reason to rebut and keep the fragile version: **the `shape:` deferral was dropped entirely.**
`_reject_unsupported_type_klass!` now checks `type:` unconditionally whenever it is declared (deferring
only to `of:`, which is genuinely unconditional and doesn't have this shape) — it never reads `validations[:shape]`
at all, so there is nothing for a lying `[]` to fool. The cost is one changed message in the case where a
`shape:`'s own container-derivation would ALSO have caught a bad `type:`: this guard's message wins now,
which is arguably the more useful one anyway (`container:` is often a key the author never wrote at all,
derived silently from a bad `type:`). One pre-existing spec (`shape_contracts_spec.rb`, a member-level
non-class-token-in-a-union case) pinned the old message and was updated to match; every other existing spec
was unaffected, since a GOOD `type:` beside a bad explicit `container:` still gets the shape's own message
(this guard only ever speaks about `type:`).

**Round-3 Codex finding (CONFIRMED, and NOT purely hostile — `to_ary` is a legitimate Ruby coercion
protocol): `_declared_type_tokens` (the union-or-single-token classifier this guard shares with the `of:`
bag's `klass:` guard) called `Kernel#Array(declared)`, which tries the value's own `to_ary` (then `to_a`)
before wrapping it.** An object defining `to_ary` therefore decided how it got read — one returning
`[String]` waved a genuinely unsupported token through as if it were a union naming a real class — and one
whose `to_ary` raised replaced the intended `ArgumentError` with whatever it threw, both reproduced by hand
before touching anything. Fixed by classifying through `case`/`when ::Array` instead (never dispatching to
the caller's own conversion methods), in the ONE shared function — `_reject_unsupported_map_axis!`'s own,
separate, now-redundant `Array(declared)` call was also simplified to call `_declared_type_tokens` instead
of duplicating the logic, closing the same gap there too as a side effect.

**Audited but deliberately NOT swept: this exact class of gap (`Array()`/`Kernel#Array` on a declared-type
value dispatching to a caller's `to_ary`) recurs elsewhere in `contract.rb`, predating this ticket** —
`_of_axis_constrains?` (the `klass:` axis's own emptiness check, PRO-3166) and `_axis_names_no_class?` (the
bare axis's, PRO-3165) both run BEFORE `_declared_type_tokens` ever sees a bag/axis `klass:` value, and both
have the identical hole for a RAISING `to_ary` specifically — confirmed by hand (`of: { klass: hostile }` and
`of: { values: hostile }` both still raise the caller's own exception instead of the intended `ArgumentError`,
even after this fix). The `type:` position itself has no such earlier competing read and is fully closed.
Sweeping every `Array()` call in this file touching a declared-type-ish value is a materially larger,
separate effort spanning PRO-3165/3166/2915/2925/3018/3068's code — flagged to Kali as a follow-up rather
than absorbed into this PR, and the one regression spec added at the bag `klass:` position pins only the
half that this fix actually closes (a lying, non-raising `to_ary`), with a comment explaining why the
raising half isn't pinned there.

Verified against every combination (block form good/bad, raw form with/without/valid/invalid explicit
container, raw form with a union, and the exact hostile-object repro at both the field and member positions)
by hand before re-requesting review a second time; pinned in `type_token_spec.rb`, including the literal
hostile-`Hash`-subclass repro as a regression spec, and mutation-tested (deleting the guard's body red-lines
every position it covers, across both `type_token_spec.rb` and the one updated pre-existing spec).

`_unsupported_type_token_message`'s `"of: "` prefix was hardcoded; widened so each of the three callers now
passes its own full spelling (`"type:"`, `"of: keys:"`/`"of: values:"`, `"of: klass:"`) — the two pre-existing
messages are byte-identical. `MAP_OF_PSEUDO_TYPES` renamed `TYPE_TOKEN_PSEUDO_TYPES`, since it is no longer
`of:`-specific.

`_reject_unsupported_model_klass!` closes the same hole for `model:`, at the same seam, right after
`ModelValidator.apply_syntactic_sugar` runs. What survives to it is everything truthy and non-String that
sugar doesn't touch — `model: 5`, `model: :nonsense`, `model: [String, nil]` — which hit the identical bare
`TypeError` on every call. Closing the union case also closes a second, quieter hole: `TypeValidator`
iterates a union happily (so the type-check side never objected), but `FieldResolvers::Model#derive_value`
calls `klass.respond_to?(finder)` / `klass.public_send(finder, id)` directly on the raw `klass:` — for
`[A, B]`, `respond_to?(:find)` is true via `Enumerable#find`, so it silently called `Array#find` instead of
either class's own finder, resolving to the wrong thing under `best_effort` rather than raising at all. No
spec/doc/downstream consumer ever used a union or a pseudo-type for `model:`, so nothing legitimate was
given up.

**Round-4 Codex findings (both CONFIRMED, both real gaps in code this PR touches, neither hostile):**

1. **`model: false`/`model: {klass: false}` (and `nil`) originally believed to already raise at
   declaration — WRONG, and the belief itself was the bug.** `ModelValidator.apply_syntactic_sugar`'s
   `options[:klass] ||= fields.first.to_s.classify` treats every FALSY `klass:`, not just the documented
   `true`/absent "please infer" spellings, as a request to infer — so `model: false` behaves identically to
   `model: true` whenever the inferred constant happens to exist, and only raises `NameError: uninitialized
   constant` (a confusing, wrong-layer error) when it does not. Reproduced by hand with `stub_const("V",
   ...)` before touching anything: `model: false` silently, successfully resolved through the stubbed class.
   Fixed with a NEW guard, `_reject_falsy_model_klass!`, that runs BEFORE the sugar's `||=` can erase the
   distinction between "explicitly false/nil" and "not supplied" — keyed on `carries_key?`, so the
   documented, spec-covered `model: { finder: :find_by_slug }` (no `klass:` at all, infers the class,
   overrides only the finder) is untouched, and `true` is excluded by identity so a hostile `==` can't fake
   it.
2. **The `type:`-deferred-to-`:of` path bypassed the round-3 `to_ary` fix entirely**, because it routes into
   `_declared_of_container!` — a DIFFERENT, pre-existing function with its OWN separate `Array(declared_klass)`
   call that round 3 never touched. `expects :v, type: hostile, of: Integer` still let a lying `to_ary`
   (returning `[Array]`) declare successfully, and a raising one still replaced the intended `ArgumentError`.
   Unlike round 3's "audited but not swept" residue (`_of_axis_constrains?`/`_axis_names_no_class?`, which
   sit on a genuinely separate, pre-existing code path for the `of:` BAG's own `klass:`/axis), this one is
   the DIRECT deferral target of this ticket's own new guard, so fixing it is squarely in scope: swapped
   `Array(declared_klass)` for `_declared_type_tokens(declared_klass)` in `_declared_of_container!` (the one
   function both of its callers — a field's `type:` and a nested bag's own `klass:` — go through), closing
   both at once.

Fixing (2) exposed a THIRD bug in round 3's own fix: `_declared_type_tokens`'s `case`/`when ::Array` swap
didn't replicate `Kernel#Array()`'s one special case (`Array(nil) == []`) — it wrapped `nil` as `[nil]`
instead, which is a harmless no-op for `_reject_unsupported_type_klass!` (both branches render the same
"got a value of class NilClass" message) but changed `_declared_of_container!`'s "no `type:` at all" message
from `"got []"` to `"got [a value of class NilClass]"`, breaking three unrelated pre-existing specs the
moment `_declared_of_container!` started reusing the fixed function. Caught by running the full suite, not
by reasoning it through — fixed by special-casing `nil.equal?(declared)` to return `[]`, matching `Array()`
for the one case that matters while still never dispatching to the declared value's own methods for every
other case.

## What shipped

- `lib/axn/core/contract.rb`: `_reject_unsupported_type_klass!` (`type:`), `_reject_falsy_model_klass!` and
  `_reject_unsupported_model_klass!` (`model:`), all called from `_canonicalize_validator_options!`; the
  `option:` prefix widening on `_unsupported_type_token_message` and its two existing callers; the constant
  rename; `_declared_type_tokens`'s `to_ary`-safe classification (reused by `_reject_unsupported_map_axis!`
  and `_declared_of_container!`, closing the same gap at both).
- `spec/axn/core/validations/type_token_spec.rb` (new): every refusal shape, every declaration position,
  both deferrals, and controls for `type:` (a Module, each pseudo-type, `Data`/`Struct`, a token that lies
  about `is_a?`, a token whose `to_s`/`inspect` raises, a token whose `to_ary` lies or raises); a second
  top-level describe for `model:` (every refusal shape, the union case, the falsy-`klass:` case regardless
  of whether the inferred constant exists, and controls including a real class/String/`model: true`/a
  Module/a `klass:`-less bag/a Module).
- `spec/axn/core/validations/recursive_of_spec.rb`: a regression spec for the `to_ary`-lying case at the
  bag `klass:` position (with a comment on why the raising sub-case isn't pinned there — a separate,
  pre-existing gap).
- `spec/axn/core/validations/nil_empty_axes_matrix_spec.rb`: the one flipped example (a `type:` bag holding
  an object that lies about `is_a?`) — the verdict now belongs to this guard rather than `allow_empty:`'s,
  since `_supported_type_token?` classifies through `case`/`when ::Module` rather than `is_a?`.
- `spec/axn/core/validations/shape_contracts_spec.rb`: one flipped example (a member's `type:` union
  carrying a non-class token beside a `shape:`) — same reasoning as above, this guard's message now wins
  since it checks unconditionally rather than deferring.
- `docs/reference/class.md`, `AGENTS-consuming.md`, `CHANGELOG.md` (three `[BREAKING]` bullets under
  `## Unreleased` → `### Fixed`).

## Verification

Full non-Rails suite (6366 examples) and the Rails dummy-app suite (368 examples) green; `rubocop` clean on
every touched file (471 files, no offenses). A/B'd the `type:` spec against `5e309e17` in a throwaway
worktree — every "refuses" example failed there (nothing raised) and every deferral/control example passed
there, so no fixture is broken in both trees. Mutation-tested repeatedly across all four review rounds:
neutering `_reject_unsupported_type_klass!` alone red-lines every position it covers (field, subfield,
ambient subfield, exposes, block-form and raw shape members) across `type_token_spec.rb` and the one
updated pre-existing spec; neutering the shared `_supported_type_token?` predicate red-lines examples in
`type_token_spec.rb`, `of_validator_spec.rb`, `recursive_of_spec.rb`, `shape_contracts_spec.rb` and
`nil_empty_axes_matrix_spec.rb` together (proof the `type:`/`of:` callers share one predicate rather than
copies of it); neutering `_reject_unsupported_model_klass!` alone red-lines its own 5 refusal examples;
neutering `_reject_falsy_model_klass!` and reverting `_declared_of_container!`'s classifier each red-line
exactly their own new regression specs, nothing else. Reproduced all four Codex findings by hand with the
exact hostile/adversarial object described before applying any fix, and reproduced each again after fixing
to confirm closure — never complied from a finding's prose alone. One self-inflicted lesson from round 4:
after redoing an accidentally-`git checkout`-clobbered set of edits (a `git checkout -- <file>` meant to
undo a mutation-test tweak discarded the real fixes alongside it), redo via `Edit` against the specific
lines, never a blanket checkout, and re-verify with the full suite before trusting the restore.
