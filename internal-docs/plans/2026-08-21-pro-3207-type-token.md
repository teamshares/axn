# A non-class `type:` token declares cleanly and raises a bare TypeError

**Status: complete.**

**Ticket:** https://linear.app/teamshares/issue/PRO-3207/axn-a-non-class-type-token-declares-cleanly-and-raises-a-bare

## Problem

PRO-3165/PRO-3166 closed a defect in every `of:` bag position: a token that is not a Class/Module, not a
union of them, and not one of `:boolean`/`:uuid`/`:params` reaches `value.is_a?(token)` and raises a bare
`TypeError: class or module required` on every call, naming neither the field nor the option. A field's own
`type:` — the most common spelling, and the last one — was left open on purpose: it is not an `of:`
position, and its sugar routes were unaudited.

Measured at `5e309e17`: `expects :v, type: false` (or `5`, `"String"`, `:nonsense`, `[String, nil]`,
`{ klass: false }`) declares without complaint and fails **every** call with the bare `TypeError`, settling
as an exception outcome reported through `Axn.config.on_exception` as an internal error.

## Design

One guard, at the one seam already shared by every `type:` spelling: `Contract#_canonicalize_validator_options!`
(`lib/axn/core/contract.rb`), which applies `TypeValidator.apply_syntactic_sugar` and is reached by both
routes a `type:` can be declared through (`_parse_field_validations` for `expects`/`exposes`/subfields/
ambient subfields/block-form shape members; `ShapeDeclaration#_symbol_keyed_member_validations` for a raw
`shape:` member). `_reject_unsupported_type_klass!` composes exactly the machinery PRO-3166 already built
and extracted for reuse — `_declared_type_klass`, `_declared_type_tokens`, `_reject_unsupported_type_token!`
(the index-based union search), `_supported_type_token?`, `_declared_type_label` — with no fourth copy of
any of it.

Two decisions, both resolved in the guard as shipped:

1. **Emptiness is folded in, not deferred.** A bag's `klass:` defers "supplied but names nothing" to
   `_reject_unconstraining_of_bag!`, because a bag has two other ways to constrain (`of:`, `shape:`). A
   field's `type:` has none, so it is the bare-axis situation instead: `type: nil`, `type: []`,
   `type: { klass: [] }` and `type: { message: "…" }` all raise here, exactly as `_reject_unsupported_map_axis!`
   folds the same case into itself for a bare `keys:`/`values:` axis.
2. **`model:` gets a dedicated, narrower guard rather than reusing `type:`'s.** It has the identical hole in
   the identical field position (`ModelValidator` builds a `TypeValidator` and delegates), but not the same
   grammar: a model class is resolved by calling a finder method **on** it, never by asking a value `is_a?`
   of it, so a union or a `:boolean`/`:uuid`/`:params` pseudo-type has nothing to dispatch through.
   `_reject_unsupported_model_klass!` requires a single Class/Module (`case klass; when ::Module`) rather
   than reusing `_declared_type_tokens`/`_reject_unsupported_type_token!`'s union-aware search, which would
   have accepted a union that only fails later — see below.

The guard defers when `of:` is also declared on the same field: `_declared_of_container!` runs
unconditionally whenever `:of` is present and already holds `type:` to a strictly narrower rule (Array or
Hash only), naming the classes that are actually legal there. Firing first would prescribe the weaker fix
and cost the author a second edit — the same deferral `_reject_unsupported_of_klass!` makes to
`_inner_of_container!`.

**Round-1 Codex finding (CONFIRMED, fixed same round): the `shape:` deferral was unconditional on key
presence, and that was wrong.** `_derive_raw_shape_container!` only calls `_shape_compatible_type!` to
DERIVE a container when the raw shape's own `container:` is nil/absent; a shape supplying its own
already-valid `container:` (`expects :v, type: false, shape: { members: [], container: Hash }`) skips
derivation entirely — `_reject_non_class_container!` passes the explicit `Hash` through untouched, and
`type:` itself is never independently checked by anything. That declared cleanly and reached
`value.is_a?(false)` on every call, the exact defect this ticket exists to close. Fixed by narrowing the
deferral to the one case that is actually still safe: `_shape_container_already_settled?` returns true only
when the shape's `container:` is both present and already a valid Module (the state in which nothing
downstream is going to look at `type:` again); every other shape state (absent, nil, or present-but-invalid)
still gets independently checked, whether by this guard's deferral to the derive-then-check path or by the
unconditional `_reject_non_class_container!` catching a bad explicit container on its own terms. Verified
against every combination (block form good/bad, raw form with/without/valid/invalid explicit container,
raw form with a union) by hand before re-requesting review; pinned in `type_token_spec.rb` with a spec that
reproduces Codex's exact repro plus one for a bad-explicit-container control, and mutation-tested (deleting
the predicate's real logic red-lines exactly the new spec, nothing else).

`_unsupported_type_token_message`'s `"of: "` prefix was hardcoded; widened so each of the three callers now
passes its own full spelling (`"type:"`, `"of: keys:"`/`"of: values:"`, `"of: klass:"`) — the two pre-existing
messages are byte-identical. `MAP_OF_PSEUDO_TYPES` renamed `TYPE_TOKEN_PSEUDO_TYPES`, since it is no longer
`of:`-specific.

`_reject_unsupported_model_klass!` closes the same hole for `model:`, at the same seam, right after
`ModelValidator.apply_syntactic_sugar` runs. `apply_syntactic_sugar` already guarantees `klass:` is never
nil/false/a String by the time the guard sees it — a falsy value falls back to the field name classified,
and a String is `constantize`d — so `model: false`/`nil` were already raising at declaration before this
ticket, just via a confusing `NameError: uninitialized constant <FieldName>` rather than an `ArgumentError`
naming the option; left as-is rather than restructured, since it doesn't exhibit the "declares cleanly,
breaks on every call" defect this ticket targets. What the guard actually catches is everything that
survives the sugar truthy and non-String — `model: 5`, `model: :nonsense`, `model: [String, nil]` — which
hit the identical bare `TypeError` on every call. Closing the union case also closes a second, quieter
hole: `TypeValidator` iterates a union happily (so the type-check side never objected), but
`FieldResolvers::Model#derive_value` calls `klass.respond_to?(finder)` / `klass.public_send(finder, id)`
directly on the raw `klass:` — for `[A, B]`, `respond_to?(:find)` is true via `Enumerable#find`, so it
silently called `Array#find` instead of either class's own finder, resolving to the wrong thing under
`best_effort` rather than raising at all. No spec/doc/downstream consumer ever used a union or a
pseudo-type for `model:`, so nothing legitimate was given up.

## What shipped

- `lib/axn/core/contract.rb`: `_reject_unsupported_type_klass!` (`type:`) and `_reject_unsupported_model_klass!`
  (`model:`), each called from `_canonicalize_validator_options!`; the `option:` prefix widening on
  `_unsupported_type_token_message` and its two existing callers; the constant rename.
- `spec/axn/core/validations/type_token_spec.rb` (new): every refusal shape, every declaration position,
  both deferrals, and controls for `type:` (a Module, each pseudo-type, `Data`/`Struct`, a token that lies
  about `is_a?`, a token whose `to_s`/`inspect` raises); a second top-level describe for `model:` (every
  refusal shape, the union case, and controls including a real class/String/`model: true`/a Module, plus a
  pin on the pre-existing `false`/`nil` `NameError`).
- `spec/axn/core/validations/nil_empty_axes_matrix_spec.rb`: the one flipped example (a `type:` bag holding
  an object that lies about `is_a?`) — the verdict now belongs to this guard rather than `allow_empty:`'s,
  since `_supported_type_token?` classifies through `case`/`when ::Module` rather than `is_a?`.
- `docs/reference/class.md`, `AGENTS-consuming.md`, `CHANGELOG.md` (two `[BREAKING]` bullets under
  `## Unreleased` → `### Fixed`).

## Verification

Full non-Rails suite (6356 examples) and the Rails dummy-app suite (368 examples) green; `rubocop` clean on
every touched file. A/B'd the `type:` spec against `5e309e17` in a throwaway worktree — every "refuses"
example failed there (nothing raised) and every deferral/control example passed there, so no fixture is
broken in both trees. Mutation-tested three times: neutering `_reject_unsupported_type_klass!` alone
red-lines the `type:` spec's 21 refusal examples; neutering the shared `_supported_type_token?` predicate
red-lines examples in `type_token_spec.rb`, `of_validator_spec.rb`, `recursive_of_spec.rb`,
`shape_contracts_spec.rb` and `nil_empty_axes_matrix_spec.rb` together (proof the three `type:`/`of:`
callers share one predicate rather than three copies of it); neutering `_reject_unsupported_model_klass!`
alone red-lines its own 5 refusal examples.
