# Changelog

## 0.1.0-alpha.5

### Field contract & subfields

* [BREAKING] Field keys are normalized to symbols, giving the contract indifferent access: `expects "note"` ≡ `expects :note`, `.call("note" => …)` ≡ `.call(note: …)`, and string keys on `expose` all resolve to the declared symbol. Splatting a string-keyed params hash into `.call(**params)` no longer silently reads `nil`. Normalization is top-level keys only; field values (including nested hashes) are untouched. A subfield's `on:` ROUTE is canonicalized the same way, so `on: "address.billing"` and `on: :"address.billing"` are one route by construction and `config.on` is always a Symbol (messages naming a dotted route print it as that Symbol). That is also what keeps the route a guard judges — the root must name a declared reader, and two subfields under one route are a duplicate — identical to the route every consumer resolves: a value whose rendering answered differently on successive reads previously had one layer clearing `:q` while the tree anchored at `:p`, so two subfields silently landed on ONE node where the honest spelling is rejected. An `as:` alias is likewise canonicalized before it is checked, so the reader name judged is the one defined. Absence still means absence, in every spelling of it: `nil`, `false`, an empty or whitespace-only String (in any encoding) and the empty Symbol are all "no route", and the field stays top-level — decided from the value's class and its own bytes rather than by asking it, since that decision is what a route whose `blank?` lied used to skip canonicalization through. `Axn::Factory.build`'s `expose_return_as` is canonicalized on exactly those terms too, so the name declared at build time and the name written from the generated `call` are one answer. And a value that is neither absent nor a name is now diagnosed as the declaration error it is rather than by accident: both options must be a String or a Symbol, and anything else raises an `ArgumentError` naming the option and the offending class (`on: must be a String or Symbol naming a parent reader (got a value of class Array)`) instead of surfacing whatever `to_sym` happened to raise — previously `NoMethodError: undefined method 'to_sym' for an instance of Array`, which named neither the option nor what was wrong with the value. That NARROWS what these options accept, and the narrowing is the point: an exotic object that merely ANSWERS `to_sym` was previously accepted and silently anchored/exposed under whatever its answer invented, independently of what the object renders as — the same two-independent-conversions defect a shape member's name is rejected for — and such a declaration now raises. Unchanged: String and Symbol names, every spelling of absence, a dotted `on:`, and a String subclass whose own `blank?` lies (still canonicalized off its bytes).
* [FEAT] `expects … on:` (subfields) now supports the full top-level option surface — `default:`, `preprocess:`, `coerce:`, `sensitive:`, `shape:`, and `user_facing:` — at any nesting depth. Subfields nest arbitrarily deep, and a dotted `on:` pulls a value out of a deeply-nested structure in one line: `expects :zip, on: "address.billing"` validates `address[:billing][:zip]` and defines a flat `zip` reader.
* [BREAKING] Dotted field NAMES are removed. Use a dotted `on:` for nested extraction (`expects :zip, on: "address.billing"`, not `expects "billing.zip", on: :address`) — it generates a clean flat reader with no `as:` ceremony. To read two values from the same wire key, disambiguate the distinct routes with `as:`.
* [BREAKING] All subfield `coerce:`/`preprocess:`/`default:` resolve on the read path, and axn never materializes or mutates the parent to apply them. A subfield transform is visible through its own reader and validation, but the parent reader returns exactly what the caller passed — `expects :note, on: :payload, default: "d"` with `payload: nil` leaves `payload` `nil` and `note` `"d"`. A subfield `default:` no longer satisfies the parent's own presence check, and a caller-supplied object is never written through its setter during validation.
* [BREAKING] Reading a subfield by method dispatch now requires `method_call: true`. The safe default reads declared data only — Hash keys and `Struct`/`OpenStruct`/`Data` members. Reaching a value that can only be resolved by invoking a method (a plain object's reader, an `Array` method, a resolved `model:` record's attribute) requires `method_call: true` on that declaration; without it axn raises a loud `MethodCallNotPermittedError` rather than silently invoking the method during validation. The same rule applies to shape-block members.
* [FEAT] A subfield whose parent is omitted or `nil` is treated as "subfields absent" — each subfield's own rule applies against `nil` (optional passes, required fails cleanly with `InboundValidationError`), instead of raising. An all-optional nested structure can simply be omitted.
* [BREAKING] Several unsatisfiable contracts now raise at class definition instead of failing (or silently reading absent) on every call: a subfield path no contract-valid input could answer; a nil-tolerant field with an unrescued required descendant; two `default:`s on one merged wire node; and a `model:` batch that also names its own `<field>_id`. Each error names the offending declarations and the fix.
* [BREAKING] A declared name with no UTF-8 rendering — a Symbol holding bytes that don't convert — is rejected, since JSON is a UTF-8 format and `JSON.generate` refuses such a property name outright. An `exposes` name raises at CLASS DEFINITION (it names a property in the serialized body whatever a schema emits); a top-level `expects` name, a subfield, or a shape member raises when the contract's JSON projection is first built (`input_schema`, `output_schema`, or `Axn::Extensions::Serialization.render`) — and at app setup for tool axns (see `Axn.validate_tool_contracts!`). Judged on the names a schema actually EMITS, so a name it never emits (a leaf on a dropped subfield, a member under a scalar `of:`) is no longer rejected for bytes that never reach a schema. Details: [Names that one JSON property can't keep apart](https://teamshares.github.io/axn/reference/class#property-name-rules).
* [BREAKING] Two declared names that render as the SAME JSON property no longer both stand: the pair collapses onto one property, which silently emitted a duplicate in `input_schema` or dropped an exposure on the way out. When it raises depends on what can see it. At CLASS DEFINITION: two field names, two `exposes` names, and two subfields under one parent (including one route spelled two ways, `on: "p"` and `on: :p`). At FIRST PROJECTION (and at app setup for tool axns): two shape members, a `model:`-generated `<field>_id` against a differently-spelled explicit one, a structured type's own members against a shape's, and two routes only RESOLUTION equates (`on: "foo.bar"` against `on: :bar` where `bar` is itself a subfield of `foo`). One wire slot named twice by the same SPELLING is a merge, stays legal, and still emits exactly one property. Six mechanisms contribute names at a node, each judged against the others — enumerated in [the reference](https://teamshares.github.io/axn/reference/class#property-name-rules).
* [BREAKING] A `shape:` graph with more than 25,000 member PATHS is rejected at CLASS DEFINITION, whether or not anything ever projects the contract. A nested shape object shared between SIBLING members multiplies out, so N levels of two-way sharing are 2^N distinct paths, and every walk of a stored graph pays one step per path: runtime shape validation walks it on each call, and `sensitive:` redaction walks it once per class — or once per logged call for a `sensitive:` that resolves against the action, which cannot be decided ahead of time. Measured with the bound removed, 786,000 paths (18 levels of two-way sharing) cost about 1.3s per log line that way, and about two seconds for the one derivation any contract makes on its first logged call. Shallow sharing is unaffected. This is a bound on the graph you declared, not on what a schema emits.
* [BREAKING] Separately, a contract whose reflected schema would name more than 25,000 JSON properties is rejected when that projection is first built (and at app setup for tool axns), before the schema is built rather than after. What counts is DERIVED from the emitter's own decisions, so anything the schema names nowhere costs nothing against it: a shape whose members never become properties (a scalar `of:` — `of: String` with `field :length` — an outbound-gated value, a value not provably member-keyed), and a whole config the projection represents nowhere (one rooted at `on: :ambient_context`, which the input schema omits entirely; a subfield under a `model:`, non-object or mixed-union parent, at any depth; a `model:` route's own declared type on INPUT, where the client sends `<field>_id` instead of the record). An `of:` element type's own members, which do reach `items`, still count — including a UNION `of:` (`of: [A, B]`), whose element types each reach `items` in their own `anyOf` branch. Two branches may still legally name the same member: they describe one property two ways, so they count toward the size without colliding. Deriving means deriving from the same view of the declaration the emitter builds from, which on OUTPUT is not the declared one: every validator entry a per-validator `if:`/`unless:` gate could skip is dropped there (a gated constraint can't be promised outbound), so an `exposes` carrying `type: { klass: SomeData, if: :flag }`, `of: { klass: …, if: … }` or a gated `shape:` names none of those properties and costs nothing — while the same declaration is still charged INBOUND, where the schema advertises the type regardless (a gate can only relax enforcement at runtime). Likewise, when one wire path is declared by two routes only the route the property is actually built from is charged, since the other route's `shape:`/`of:` is never emitted; and a field the input schema skips by name (`ambient_context`, reachable only by assigning a config onto a class) costs nothing. What is counted is one emitted PROPERTY PATH, not one declaration, so several declarations that legally name ONE property cost one: a `shape:` member beside a same-named subfield, two routes to one wire path, a `model:`-generated `<field>_id` beside an explicitly declared one, a `Data` type's member overlaid by a same-named shape member — each is a single key in the emitted schema, and each used to be charged twice, so a contract of such merges was rejected at two-thirds of the cap. In the other direction, every intermediate key a dotted `on:` introduces is now counted too (they are shared nodes, counted once each however many subfields pass through), so a contract that names thousands of properties through deep `on:` paths is bounded rather than left to build them. The count is therefore exactly the number of properties the schema emits.
* [FEAT] A failing call now collects every violation across top-level fields, subfields, and model-consistency and reports them together, and each nested-subfield failure names the stranding hop (`'payload.address' is nil, so nested expectations beneath it cannot be satisfied`).
* [BREAKING] `readers:` is removed — every declared field generates a reader. Use `as:`/`prefix:` to rename a colliding reader.
* [FEAT] `as:`/`prefix:` rename a field's generated reader independently of the wire key (`expects :channel, as: :raw_channel`), freeing the name for your own method; `prefix:` renames several subfields at once (`prefix: :event_`).

### Validation, coercion & schema

* [FEAT] `coerce:` parses an inbound wire string into a field's declared Ruby type before validation, so a JSON or form client sending `"2026-07-08"` or `"123"` is accepted for a `Date`/`Integer` field. Coercible types are `Date`, `DateTime`, `Time`, `Symbol`, `Integer`, `Float`, and `:boolean`. Coercion is opt-in per field and coerce-or-leave (a real Ruby value passes through; an unparseable string fails validation normally, reported as "could not be coerced to a Date"). No effect on `input_schema`/`output_schema`.
* [FEAT] `coerce_input_types` (a per-class-overridable config setting) turns on `coerce:` for every coercible top-level field and subfield of an action — for a fully transport-facing action such as a controller handing it a params hash or an adapter decoding JSON — without annotating each field. A field's own `coerce:` always wins.
* [FEAT] Tolerance flags now combine with a scalar validator value: `expects :num, numericality: true, optional: true` (and likewise `inclusion:`/`format:` under `optional:`/`allow_nil:`/`allow_blank:`) work instead of raising a `TypeError`.
* [FEAT] Conditional validation: `expects`/`exposes` (and shape members) accept `if:`/`unless:`. The condition gates every validator including the implicit presence check, so requiredness itself can be conditional — expressing the conditionally-required-subfield pattern (`expects :user, on: :data, if: -> { data.present? }`). `error`/`success` and the `on_*` callbacks now also accept `if:` and `unless:` together (combined with AND).
* [FEAT] `MyAxn.input_schema` / `MyAxn.output_schema` return JSON Schema derived from `expects`/`exposes` (subfields, `model:`, `of:`, `shape:`, `inclusion:`, defaults, unions), and `Axn::Extensions::Serialization.render(result)` renders a `Result` to a JSON-safe Hash — one definition an adapter can turn into an MCP `inputSchema`, an LLM `parameters` block, or an OpenAPI schema. Read-only and off the execution path; `sensitive:` has no effect on schema output.
* [BUGFIX] A bare-Array `inclusion:` shorthand (`inclusion: %w[a b c]`) now reflects into `input_schema`/`output_schema` identically to the `{ in: [...] }` / `{ within: [...] }` long form — emitting the `enum` and inferring the member type, and contributing its nil-membership to the field's nullability/requiredness (a bare set containing `nil`, and a bare `exclusion:` set not containing `nil`, are now correctly read as nil-tolerant). Previously the bare form validated at runtime but reflected as an unconstrained `{}`, leaving schema looser than runtime.
* [FEAT] `allow_empty:` declares the emptiness axis independently of nullability, so all four requiredness contracts are expressible: `allow_empty: true` keeps a field required and non-nil while accepting an empty collection or string (previously reachable only as a side effect of `presence: false`), and `optional: true, allow_empty: false` accepts an omitted or nil value while rejecting an empty one (previously raised at declaration). It requires a `type:` whose values can be empty — `Array`/`Hash`/`Set`/`String`/`:params`, or any class or module defining `empty?` — and accepts only `true`, `false` or `nil`, so a typo such as `allow_empty: "false"` raises rather than reading as truthy and meaning the opposite. Emptiness is `empty?`, not `blank?` — a whitespace-only String is not empty, and the check asks the value's own `empty?` rather than measuring a length, so it holds for a `type: :params` value that reports none.
* [BUGFIX] A field that rejects empty values now reflects that into `input_schema`/`output_schema` as `minItems`/`minProperties`/`minLength`, reading every `length:` spelling ActiveModel resolves into a floor (`minimum:`, `is:`, `in:`/`within:`, and the implicit floor of a blank-intolerant entry). Previously a required `type: Array` rejected `[]` at runtime while its schema advertised `[]` as acceptable, leaving schema looser than runtime. Emission is derived from the property's final emitted type (so a shaped custom class is floored as an object, not a string), covers union `anyOf` branches and `output_schema`, and is withheld wherever an empty value can pass the validator set as a whole. An empty container used as a `default:` is recognized as empty — including a subclass that inherits its `empty?` — so such a field is no longer advertised as omittable while every omitted call rejects it.
* [FEAT] `allow_empty:` is never silently defeated by something else in the same declaration. It is honored alongside an author-declared `length:` that permits an empty value (`length: { maximum: 3 }`, `length: false`), it makes an author-declared `length:` floor fire on the empty value even under `optional:`, and it applies to `type: :params`, which takes no default presence check. Where the declaration answers the emptiness question two different ways — an explicit `presence:` that disagrees with the flag, or a `length:` that explicitly admits an empty value (`minimum: 0`, `is: 0`, `maximum: 0`, a range starting at 0, its own `allow_blank: true`) — it raises at declaration naming both spellings, instead of letting one answer win silently.
* [BUGFIX] A field's `optional?` and its schema requiredness now answer one shared question ("do this field's validators accept nil?"). A field that rejects nil by type alone was previously reported as optional while the schema listed it as required — most visibly a bare `type: :boolean` or `type: :params` field, which skips the default presence injection so its only validator is the type check: either used to report `optional? == true` while both the schema and the runtime treated it as required (an omitted `flag` raises "Flag is not a boolean"). This is not total: a field carrying a usable literal `default:` still reports `optional? == false` while the schema omits it from `required` (a deliberate, unchanged divergence) — the two now agree on nil-tolerance specifically, not on every input to omissibility.
* [BUGFIX] A `nil` rejected by a field's `type:` now produces that one error instead of also running every other validator against the nil — a custom `validate:` written for a real value no longer contributes a derivative "failed validation" message alongside the type error.

### Shape blocks

* [FEAT] Shape-block members accept `sensitive:` (redacted from logs, exception context, and `inspect` — precisely by member name for Hash values, wholesale for non-Hash values the filter can't descend into), `method_call:`, `if:`/`unless:`, and `user_facing:`, all with the same semantics as a top-level field.
* [FEAT] `Axn.validate_tool_contracts!` validates every registered tool axn's contract in one pass and raises on the first invalid one, naming the offending class. Under Rails the engine calls it at `config.after_initialize` and on every `config.to_prepare`, so an invalid tool contract is a boot (or reload) failure rather than something a user's tool call discovers; without Rails an app calls it itself, typically after requiring its action files. Enumeration honors both halves of tool membership, so a `tool`-DSL axn is covered with no tool root configured at all; what bounds coverage is documented on the method — at least one adapter must be registered, and a tool outside every configured root is only covered once something has loaded it (always true under eager loading, not in a lazily-loading development environment), and a Zeitwerk directory whose load aborted takes its unvalidated siblings with it. Everything not reached falls back to validating on first projection, which is where every non-tool axn is validated anyway. Naming the tool cannot cost you the error, and which exception you get is decided from the METHOD TABLE rather than by running the exception's code. An ordinary contract failure — an `ArgumentError`, a `DuplicateFieldError`, an exception that builds its message from its own state — is re-raised as ITSELF, renamed to name the tool, with its class and state intact. One whose class (or singleton) supplies its own `#exception` or duplication hook, or that is frozen, is not renamed at all: it surfaces as `Axn::InvalidToolContract`, which names the tool, repeats the original's message, and carries the original as `cause`. That is the only way to terminate — renaming ends in `raise`, which dispatches the 0-arg `#exception` on whatever object it is handed, and no guard can wrap that dispatch (an override answering itself once and raising the second time destroyed the failure at boot, since `Exception#exception` clones and `raise` then asks the clone). `#message` is a separate question, read only behind a guard: a hostile one degrades the message (to the exception's stored message, or to its class) while the class and `cause` survive. What the message HOLDS is foreign too, so every string this report writes into prose — the message, the tool's own constant path — is rendered into UTF-8 rather than joined to it (see below): guarding each dispatch is only half of what a report needs, since a `#message` that behaves perfectly and hands back bytes a UTF-8 message cannot carry made the interpolation itself raise.
* [BUGFIX] A declared name whose bytes are not UTF-8 (a valid ISO-8859-1 Symbol) no longer breaks the messages that name it. Every layer that writes a name into prose now renders it as the JSON property it canonicalizes to: a validation error naming shape members in two encodings was unreadable — `.message` itself raised `Encoding::CompatibilityError`, so a caller could not read its own failure and anything logging `e.message` raised too — the nil-tolerance contradiction error raised while naming the stranded path, and the call logger silently lost its line when caller data carried Hash keys in two different non-ASCII encodings. A foreign CLASS name is rendered on the same terms and through the same path (`Café` reads as its text, unrenderable bytes are escaped): a constant may hold non-UTF-8 bytes — `const_set` accepts them and a Latin-1-encoded source file declares them — so naming a class raised `Encoding::CompatibilityError` from the very messages that fall back to naming one, which is the safe escape the rest of this rests on. That covers the `sensitive:`/shape-member-name rejections, an uncopyable option container, a nameless or re-walked shape member, a declared type named in a collision report, and `Axn.validate_tool_contracts!` naming the tool. Two message paths keep the raw bytes and are named here rather than glossed: `UnserializableValue#message` (which names the offending value's class) and the two-keys-collapse report (which names both keys' classes). Both live below the renderer in the load order — `Reflection::Values` and `axn/exceptions` are what the renderer itself is built on — so rendering there needs the byte primitive moved down first. Names and class names that are ASCII render byte-identically, so ordinary messages are unchanged. (Non-ASCII on both sides is what triggered it; ASCII beside Latin-1 concatenates fine.)
* [BUGFIX] `input_schema` no longer raises `Encoding::CompatibilityError` when a deep subfield with a non-UTF-8 name (a valid ISO-8859-1 Symbol) is omitted from the schema — the warning naming those subfields interpolated their raw bytes into a UTF-8 message, so reflecting the schema blew up over a subfield the warning only mentions in passing. Names are rendered as the JSON property they canonicalize to, as every other message does.
* [BUGFIX] A declared name can no longer replace the property-name verdict against it with an exception of its own. Every step from "these two names are one property" to the raised `Axn::DuplicateFieldError` now compares and renders names without running a line the name's author wrote: attribution matched emitted paths with `Array#==`, the contract chose between its two duplicate wordings with `==`, and the size guard decided which of two configs the schema builds a shared wire key from by handing the name to a Hash and letting its own `hash`/`eql?` answer — so a name defining any of them raised INSTEAD of the report, and a `NotImplementedError` (outside `StandardError`) escaped every rescue meant to settle it. The canonicalization those rules judge on reads a String's own bytes and a Symbol's own rendering rather than dispatching `to_s` — which is sound because a name whose bytes and rendering can DIFFER is no longer admitted at all (below) — and that fixes three things at once: a single field name whose `to_s` raised took down a projection it named exactly one property in, a collision involving one was reported as its exception, and — because a name was canonicalized to REACH the unrenderable-name check and canonicalized again inside it — a `to_s` answering differently the second time walked a name with no UTF-8 rendering straight past the check, and the emitted schema then advertised a property the contract does not have: `JSON.generate` asks a key's own `to_s` too, so it named whatever the name last claimed, while the SAME bytes under a name that renders them honestly were rejected. On the declaration path the same double-ask made a duplicate go unreported entirely. Reachable only through a config ASSIGNED onto a class (`internal_field_configs=`), which is the one route a raw name reaches these rules by, since the DSL symbolizes every declared name; two names that are the same content in two objects still MERGE onto one property, exactly as two identical spellings do, and every other verdict and message is byte-for-byte unchanged.
* [BREAKING] A declared name that decides its own RENDERING is refused as a property name: it must be a Symbol, or a String that has not redefined `to_s` (on its class or as a singleton). This is the premise the other two name rules rest on — a name has to mean ONE property — and three separate readers pick between a String's two candidate names: the rules canonicalize it by its bytes, the reflected schema lists it in `required` through its `to_s`, and `JSON.generate` renders a Hash key through that same `to_s`. So a `String` subclass holding the bytes `"other"` and rendering `"dup"` passed the collision rules beside a `:dup` field and then emitted `{"properties":{"dup":{},"dup":{}}}` — two declarations, one JSON property, one of them silently dropped by any parser, which is exactly the collapse these rules exist to reject, reached through the encoder instead of through a declaration. Choosing the other candidate instead would only have swapped which half was wrong (a name whose bytes have no UTF-8 rendering but whose `to_s` renders fine would ship a property that is neither), so the name is refused rather than reinterpreted — by OWNERSHIP, read from the method table, which runs none of the name's own code and needs no assumption that a rendering agreeing with the bytes today will agree tomorrow. A Symbol is unaffected and cannot be affected (it takes no subclass instance and no singleton, so `to_s` is always Symbol's own); a plain String, and a String subclass that has NOT redefined `to_s` (which renders the receiver's own bytes), are unaffected too, including the merges and collisions they take part in. It fires where the emitter keys a property by the name itself — a top-level `expects`/`exposes` field — and raises when the projection is first built (`input_schema`, `output_schema`, `render`), or at app setup for a tool axn; a subfield's wire segment, a shape member's key and a `model:`-generated `<field>_id` are interned from the name's rendering by the emitter, so those name one property already and nothing about them changes. Reachable only through a config ASSIGNED onto a class, since the DSL symbolizes every declared name.
* [BUGFIX] The reflected schema's top-level `required` list can no longer name a property its own `properties` map does not define. A `required` entry was rendered by dispatching the declared name's `to_s` a second time, so a name answering differently there than as a Hash key produced a schema no input can satisfy — a plain String carrying a singleton `to_s` did it with a single declaration (Ruby stores a plain String Hash key as a frozen copy of its bytes, so only the `required` entry was diverted). Both artifacts now read the one name once, exactly as a shape member's `required` entry has read the one Symbol its property is keyed by. Ordinary Symbol-named fields are byte-for-byte unchanged.
* [BUGFIX] A declared contract no longer changes after the class is declared. A raw `shape:` Hash (its members list, each member's `validations`/`metadata`, and any nested shape) is deep-copied at declaration, as are the `of:`/`validate:`/`inclusion:` option containers — previously axn stored the caller's own objects, so a builder Hash reused across two declarations retroactively gave the FIRST class members appended after it was declared, mutating a nested shape changed an already-declared contract, and swapping a `validate:` bag's `:with` changed which validator a declared field runs. A raw member's own option containers are detached on exactly the same terms as a field's, so mutating an `inclusion:` list after declaring cannot widen a member's enum either. Objects are copied rather than frozen, so reusing or extending your own is still fine. What CAN be copied is decided from the method table: a container that defines methods of its OWN is refused at declaration (naming the option, the offending methods, and telling you to pass a plain Array or freeze yours) rather than copied and checked. `dup` copies an Array's elements while SHARING its instance variables and dropping its singleton class, so the copy answers as you declared only where every answer is Ruby's own — a set whose `include?` reads its own identity, an ivar, or a singleton method accepts what you declared and its copy does not, and the copy IS the stored contract, so the class then rejects the values you declared as valid. The question is asked of the whole container rather than of a list of predicates, because the same copy path also stores a `type:`/`of:` list that axn reads with `Array(…)`/`any?`, and it is asked through the object's singleton class, so a subclass method, an extended module and a singleton override are one answer. A FROZEN container is stored as it is, with no copy at all: nothing can mutate it afterwards, which is the only thing the copy protects against. So a container that answers membership with its own code stays legal by being frozen, and a plain Array (or a subclass that adds no methods) is copied exactly as before. This is deliberately stricter than verifying the copy, which cannot be done: a hook that dropped a lookup index held every declared element and rejected them all (caught by comparing elements) — and then a hook that dropped only the index of accepted NON-elements (a set holding `"canon"` and aliasing `"alias"` to it) passed every element-based check while the declared contract had silently stopped accepting the aliases. The accepted set is whatever the container's code says, so it is not enumerable from outside; ownership is a fact that needs no code run to establish. A membership container that is NOT an Array (a `Set`, a `Range`, an object answering `include?`) is neither copied nor refused: it is stored as your object and answers membership itself, so a mutable one is still yours to widen after the class is declared. Shape MEMBERS are copied on the same terms as everything else, whatever object they are: each one's `field`, validations, metadata, `sensitive:`, `user_facing:`, `method_call:` and `description` is read once and stored in axn's own `ShapeConfig`, so a duck-typed member of your own — and the nested `shape:` and option containers it carries — is snapshotted rather than shared.
* [BUGFIX] Every shape member is snapshotted into axn's own `ShapeConfig` at declaration, so a member object handed to a raw `shape: { members: [...] }` is no longer stored live — closing the last place a declared contract still depended on an object you hold. Two defects shared that root. `sensitive:` was read per derivation, and the table redaction derives from a declaration keys on the identity of the field-config arrays (which nothing inside your member changes), so flipping `sensitive:` after the class was declared took effect or did not depending on nothing but whether anything had asked yet: read the contract once first and a member declared `sensitive: false` stayed in the clear whatever you set it to, read it only after and an already-declared contract retroactively started redacting. And the canonical copy of a member's `validations` was computed and then thrown away, so a member declared with String keys (`{"type" => {"klass" => String}}` — what a params-derived or `with_indifferent_access` Hash gives you) reflected as an unconstrained `{}` while every call raised `ArgumentError: must supply :klass`: two layers, two answers, neither of them the declaration. Both are fixed by reading each value ONCE, on its way into the snapshot — `field`, canonicalized `validations`, `metadata`, `sensitive:`, `user_facing:`, `method_call:`, `description` — so reflection and the runtime validator read one canonical form and nothing about a declared member changes afterwards. The nested `shape:` a member carries is snapshotted with it (mutating that nested Hash after declaring no longer changes a declared class, which was a documented residue until now), a member's own option containers are detached for real (appending to a duck-typed member's `inclusion:` list can no longer widen its enum), and a stored member name is always the Symbol every consumer keys it by, for a duck-typed member exactly as for a `ShapeConfig`. A reader that answers differently on successive reads no longer splits a guard from its consumer either: the first read IS the contract. Neither does a NAME that CONVERTS differently on successive reads, which is the same defect one step in — `to_sym` is a second dispatch on the caller's own object, so a member whose name canonicalized to `:alpha` for the duplicate check and `:collide` for the stored config left two declared members under one property, one property emitted, and nothing raised. The canonical Symbol is now computed once, beside the check that judges it, and stored. Two more consequences: `output_schema` no longer raises `NoMethodError: undefined method 'with'` for an `exposes` member carrying a per-validator `if:`/`unless:` gate (the outbound emitter views a gated config through a copy of itself, which only axn's own config types answer to), and a member's `description` is honored whether it answers the reader or carries it in `metadata`.
* [BREAKING] A raw `shape:` member's `#default` reader is no longer read. `default:` is not part of the member grammar — a member is reader-less, the block form rejects it outright, and nothing applies one at runtime — but a duck-typed member defining the reader had it emitted into the reflected schema anyway, which made that schema LIE: it advertised the member as optional carrying a default, and the omitted call then failed presence validation. Such a member now reflects as required with no `default`, matching what a call actually does. `#description` is still honored, whether the member answers it directly or carries it in `metadata`.
* [BREAKING] An `of:`/`validate:`/`inclusion:`/`exclusion:`/`type:` option container that is an Array SUBCLASS defining methods of its own — most obviously its own `include?` — now raises at declaration unless it is frozen; it used to declare cleanly. Freeze it (`.freeze`, and it is stored as your own object, membership behavior and all) or pass a plain Array. This is the loud form of the bugfix above: such a container was copied at declaration and the COPY became the contract, and `dup` does not carry the identity, the ivars or the singleton methods its `include?` may read — so a set that accepted `"ok"` silently became a contract that rejected `"ok"`, and a `type:` list read with `Array(…)`/`any?` silently became a type nothing matched. A plain Array, a frozen container of any class, and a subclass that adds no methods are all unaffected.
* [BUGFIX] Every layer now reads a `shape:`'s member list through one shared capture (`each`), so schema reflection, the declaration guard, runtime validation, and `sensitive:` redaction cannot see different members. An Array subclass answering `filter_map`/`flat_map` differently from `each` previously made `input_schema` emit no member properties while the guard and validator saw them — and, more seriously, dropped a `sensitive:` member from the redaction set, logging its value in the clear.
* [BUGFIX] An option bag keyed by STRINGS — what a params-derived Hash or `.with_indifferent_access` produces — now validates as declared. Bag keys are axn's own grammar (`klass:`, `in:`, `with:`, `minimum:`) and every consumer, axn's validators and ActiveModel's alike, reads them as Symbols, so a String-keyed bag answered nobody: `type:`, `inclusion:` and `length:` declared cleanly and then rejected the values they were declared to accept, `model:` resolved a class inferred from the field name rather than the one declared, and `of:` raised "must supply :klass". Keys are canonicalized at declaration (a bag naming one option under both spellings is rejected rather than silently dropping one); values are untouched, so an `inclusion:` list keeps its own class and its own `include?`. A String key on the DECLARATION itself (`expects :a, "type" => String`) is still an unknown key, as before.
* [BREAKING] An option container that answers a missing key from a Hash DEFAULT (`type: Hash.new(String)`, or one carrying a `default_proc`) now raises at declaration; it used to declare cleanly and then fail on every call. The options such a Hash supplies are not among its entries, and every container axn stores is copied entry-wise (see the bugfix above), so nothing the default answers reaches the stored contract — and nothing downstream could honor it anyway: ActiveModel rebuilds each validator's options into a Hash of its own, so `type: Hash.new(String)` raised `ArgumentError: must supply :klass` on every call, naming a key the author did supply, both before axn copied bags and after. The rule is on the CONTAINER rather than on a missing key, because a bag holding real entries beside a default also answers every key it does NOT hold — a `type:` bag with a default is `if: <default>` too, a truthy gate nothing declared. It applies wherever a declaration stores a caller's Hash: each validator's option bag on a field and on a raw shape member, a raw `shape:` node (top-level or nested), and a member's own `validations`/`metadata`. `default`/`default_proc` are read through Hash's own readers, so a subclass denying its default is still refused. It applies under every KEY SPELLING, which took closing separately: canonicalizing String keys (see the bugfix above) REPLACES the bag with a plain copy of its entries, and a plain copy has no default — so the check read a Hash the defect had already been erased from, and a String-keyed, mixed-key or `HashWithIndifferentAccess.new(<default>)` bag declared silently while its Symbol-keyed twin was refused. Canonicalization now leaves such a bag exactly as it came, so the check that owns the rule judges what the author wrote. Write the entries out (`type: { klass: String }`); an ordinary Hash literal has no default and is unaffected, `.with_indifferent_access` on one included.
* [BREAKING] A raw `shape:` member must answer to BOTH halves of the documented contract (`#field` and `#validations`), and is rejected at class definition when it does not — runtime validation reads both for every member it validates, so such a member declared cleanly and then raised `NoMethodError` on the first call. Relatedly, a raw `shape:` must supply `members:`: an absent or nil list is rejected at class definition too (it used to fail on the first call), while an explicitly empty list stays legal, since the declared type still constrains the value.
* [BUGFIX] Schema reflection now honors that same contract, and nothing beyond it. A member implementing only `#field` and `#validations` reflects, where it previously declared cleanly and then raised `NoMethodError` from `input_schema`/`output_schema` because the emission path dispatched `#description` unconditionally. Every attribute beyond the two (`#description`) is read as optional, so declaration and reflection accept the same members. A member that defines them is unaffected.
* [BREAKING] `model:` on a shape member now raises at declaration, whichever route declared it — a `do … end` block or a raw `shape: { members: [...] }` — since a member is reader-less and never resolves a record. Use `type: Klass` for a plain instance check. On the raw route it previously declared cleanly and then failed every call with `ArgumentError: must supply :klass`; it is refused rather than expanded into a bag (see the shorthand bugfix below), which would have made the option silently type-check the element in place.
* [BREAKING] A raw `shape:` member's `user_facing:` is held to its grammar at CLASS DEFINITION, alongside its name and its `sensitive:`, rather than on the first call that happens to fail that member. A malformed value (`user_facing: 123`) previously declared cleanly and then raised from validation whenever that member failed — a declaration defect detonating on production data instead of at the author. Only a TRUTHY value outside the grammar is affected; `nil`/`false` remain "not opted in", and a member carrying no `#user_facing` reader at all is unchanged. A DECLARED contract can no longer reach the runtime check at all — every stored member is a `ShapeConfig` axn constructed from a value it grammar-checked, nested shapes included — but the check stays, for the one route that passes no declaration walk: a field config array assigned onto a class directly carries the caller's own member objects, exactly as it carries an unwalked shape graph. There the value is checked where it is read, because it does not merely produce a wrong message: a truthy non-rule reclassifies the violation as user-facing, so the contract bug settles as a plain failure and is never reported, and `user_facing: 123` then surfaced the literal `"123"` to the caller. `Axn::Core::Contract::FieldConfig`'s constructor now holds a FIELD's `user_facing:` to the same grammar, alongside the `sensitive:` it already held — that is the choke point every stored field config passes, declared or assigned, so the same defect on a field (which no runtime check covered either) is refused before the config exists. The grammar check itself now decides and REPORTS without running the value's own code, matching the `sensitive:` guard beside it: the `true`/`false`/String/Symbol arms are `case`/`when` (`Module#===`) rather than `is_a?`, the callable arm still asks the invoker's own `callable?` — so what may be declared stays exactly what will be invoked, duck-typed callables included — but a value that raises while being asked is refused rather than allowed to replace the verdict with its own exception, and the offender is named by CLASS instead of by `inspect` (`got a value of class Integer`, not `got 123`). Two consequences: a value claiming String through its own `is_a?` is now rejected (the executor picks its String arm by `case`/`when` too, so such a value was accepted and then rendered as a literal), and a `NotImplementedError` raised from a declared value's `is_a?`/`respond_to?`/`inspect` no longer escapes the declaration as itself.
* [BREAKING] A shape member's name is normalized to a Symbol at declaration, as a top-level field name already was: `field "bar"` stores `:bar`, so `ShapeConfig#field` is always a Symbol (and `sensitive_fields` reports Symbols for members). A member name must now be a String or a Symbol — any other object is rejected at declaration, because a member name is both the JSON property it renders as (`to_s`) and the schema property key it is emitted under (`to_sym`), and only those two types make those conversions each other's inverse. Previously an object whose `to_s` and `to_sym` disagreed declared cleanly and then had one of two members silently discarded from the reflected schema. Emitted schema properties, runtime validation (both string- and symbol-keyed input), and `sensitive:` redaction are unchanged; a `field :a` / `field "a"` pair is now reported as the duplicate NAME it is rather than as two names collapsing onto one property, matching how `expects :foo, "foo"` has always been reported.
* [BREAKING] Two members under the same parent — or two top-level members of one shape — may no longer share a name (rejected at class definition, since one members list settles it), or carry two names that render as the same JSON property (rejected when the projection is first built, since that is what reveals the collapse). Members of different parent blocks never collide even at the same depth: a `zip` declared inside a `from` block and a `zip` declared inside a `to` block are properties of different objects. Declaring the same member twice previously built both members and kept only the last in the reflected schema, discarding the first with no signal.
* [BREAKING] A shape's `container:` must be a class or module. A raw `shape: { container: … }` naming anything else previously declared cleanly and then failed EVERY call with a bare `TypeError: class or module required`, since the container is what the shaped value is type-checked against; it now raises at class definition naming the value and the fix. An omitted `container:` is still derived from `type:` as before.
* [BREAKING] An untraversable `shape:` graph now raises `ArgumentError` at class definition instead of overflowing the stack while the class is being defined (`SystemStackError` is outside `StandardError`, so no rescue could settle it). Declaring one is now the only way to meet it: the walk snapshots what it accepts, so a graph a class HOLDS cannot become self-referential afterwards. A field config array assigned onto a class directly, bypassing `expects`/`exposes`, still carries whatever shape its author built — so the projection, redaction and ambient-placement walks over stored configs stay bounded and report it the same way, rather than overflowing there. Redaction's masking walk is bounded by the VALUE rather than by the graph, because it descends both together: under a stored self-referential graph, a self-referential value is masked wholesale where it repeats (`[FILTERED]` — never passed through, since a cycle is exactly where a `sensitive:` sibling would otherwise print in the clear), while an acyclic value is still followed to its own leaves however often the graph repeats, and a value merely repeated among siblings is still masked in full at every position. Two forms: a graph reachable from inside itself, reported against the member that closes the loop; and a shape object that builds a fresh nested shape on every read, rejected past 64 levels of nesting — deeper than any hand-written shape block goes. The 64-level bound is judged over the graph you DECLARE, not over the route the declaration walk happens to take: a nested shape the walk has already verified is re-judged by its own height wherever it is reused, so a graph whose depth is assembled out of shared sub-shapes each first reached shallow (no walk of it descends past two levels, while the graph it stores is 70 deep) is rejected where you declared it. Such a contract had no honest schema anyway — the first projection refused to walk it — and it also redacted values it should have logged: past the depth bound `sensitive:` masking answers "assume a secret" (nothing can enumerate a graph that mints its members on demand), so a stored graph past the bound masked a value in a contract with no `sensitive:` anywhere in it. Relatedly, the member-name and `user_facing:` declaration guards over a raw `shape:` kwarg now decide types and reader membership from the real class and method table (and read a `method_missing`-served reader the way reflection does), so a member or shape Hash overriding `is_a?`/`respond_to?`/`key?`/`nil?`/`==`, or answering only through `method_missing`, can no longer skip a guard that reflection's own walk still consumes, nor replace its declaration error with an exception of its own. A raw shape's `:container` is likewise derived from `type:` regardless of what the shape claims about itself, so a lying shape Hash no longer declares cleanly and then raises `TypeError: class or module required` on every call.
* [BREAKING] A raw `shape:` member's validator SHORTHAND is expanded at declaration, and held to the same compatibility guards, exactly as a declared field's is — so the spelling every author writes by hand now works instead of failing, and a member option that constrained nothing is now refused at class definition rather than accepted silently. `type: Hash` (rather than `type: { klass: Hash }`) validated nothing and raised `ArgumentError: must supply :klass` on EVERY call; `of: Hash` did that AND took `input_schema`/`output_schema` down with `ArgumentError: odd number of arguments for Hash` (and so `Axn.validate_tool_contracts!`, which projects every tool axn's contract at app setup), since the projection reads that option as a bag in three places and a Class asked for `[:klass]` is a Hash constructor call; and a member carrying both a bare `type:` and a nested `shape:` raised `TypeError: #<Class:Hash> does not have #dig method` from the projection, naming neither the member nor the option. `#field` + `#validations` is the whole member contract, so nothing had ever expanded a raw member's bag — its KEYS were canonicalized and its containers detached, but the values were left as spelled — while every consumer, axn's validators and the projection alike, reads `[:klass]`/`[:with]`. The expansion is the DSL's own (each validator owns the expansion of its own shorthand) and runs at the same point in the same order, after the bag's keys are canonical and its containers detached, so a bare `type: [Foo, Bar]` stores a copy of that list exactly as a field's does. The emitted schema for a bare spelling is now identical to the canonical bag's, inbound and outbound, its declared type's own members included. Expanding the shorthand is only half of it: the two guards that read the canonical bag — `of:` requires `type: Array`, and must name an element class — run in the same seam, so a member is refused for exactly what a field is refused for. That is what makes this BREAKING, and the change to check before upgrading: a raw member declaring `of:` beside a non-Array `type:` (or with no `type:` at all) used to declare cleanly and pass every call, with the element constraint silently inapplicable — `of:` is only ever consulted for an Array value — and now raises `ArgumentError` at class definition, naming the declared type; one declaring `of: nil` used to declare and then raise `must supply :klass` on every call, and now raises the same message at the author. (`of: false` is unchanged and still inert on BOTH routes — the required-option check is `nil`-valued, and a field has always behaved the same way.) Two further consequences worth naming: a `validate:` Hash carrying no callable is now rejected at declaration rather than on every call, and `model:` — the one shorthand a reader-less member has no meaning for — is refused rather than expanded (see above). The same parity now holds one level down, for a member's NESTED `shape:`: its `container:` is derived from the member's own `type:` exactly as a field's is derived from the field's, and a non-class one is refused exactly as a field's is — at every nesting depth, which also closes the same two holes below the top node of a FIELD's raw `shape:`. Both used to be reached only on a call: a hand-written nested `shape:` with no `container:` (the natural spelling, and one the `do … end` form derives for you) declared cleanly and then failed EVERY call with a bare `TypeError: class or module required`, naming neither the member nor the option, and now validates as the block form does; a nested `container: :junk` did the same and now raises at class definition with the message a field's already gives. That is the other change to check before upgrading, together with its corollary: a nested `shape:` whose member declares no structured `type:` to derive a container from now raises `a shape block requires a single structured type:` at class definition, where it used to declare and fail every call the same way. The last thing a member's bag was never held to is its KEYS — the check that would have caught several of the above wholesale. A raw member's bag never passes the field path's option parse, so nothing checked what was IN it: `{ tpye: String }` declared cleanly and raised `ArgumentError: Unknown validator: 'TpyeValidator'` on EVERY call — naming a class the author never wrote, and neither the member nor the option — while the same typo on a field is refused at class definition. Same for the field-level options someone naturally reaches for inside a member bag: `optional:`, `default:`, `preprocess:`, `sensitive:`, `user_facing:`, `method_call:`, `as:`, `prefix:`, and a registered metadata key such as `description:`, each declared and then died per call under a validator class named after the option (`OptionalValidator`, `SensitiveValidator`). All of them now raise at class definition, naming the member and the key — and the four the block form already refuses with a REASON (`default:`/`preprocess:` have no resolution target on a reader-less member; `as:`/`prefix:` rename a reader it has not got) keep that reason on this route, since an author who wrote `default:` has a different problem from one who wrote `tpye:`. Everything else gets one message saying where a member's other options actually live: `sensitive:`/`user_facing:`/`method_call:` are read from the member itself, `description:` and any registered metadata from its `metadata`, and the tolerance the block form spells `optional:` is `allow_blank:`/`allow_nil:` in the bag. The allowed set is DERIVED rather than listed again — the field path's own recognized keys unioned with ActiveModel's own shared validation options, which is what a raw bag reaches `validates` as — so it cannot drift from either source, and `if:`/`unless:`/`on:`/`strict:`/`allow_blank:`/`allow_nil:` keep working on a member exactly as before. `coerce:` goes the other way and is now refused on a member in BOTH its spellings, whichever route declared it: it resolves a coerced value onto a reader a member has not got, so a top-level `coerce:` used to reach ActiveModel as a validator and fail every call, while `type: { klass: …, coerce: true }` was accepted and silently did nothing (`coerce: false` inside a type bag stays the legal no-op it is on a field). Every one of these applies at every nesting depth, since the check runs per member wherever the declaration walk descends.

### `model:` fields

* [FEAT] A `model:` field now also defines a `<field>_id` reader that returns the record's primary key, whether the action was called with `user:` or `user_id:`. It's alias-aware and triggers no extra lookup.
* [BREAKING] Passing both a `model:` record and a contradictory `<field>_id` (default `:find` finder) now raises `InboundValidationError` instead of silently preferring the record. Passing one, or both in agreement, is unchanged.
* [FEAT] A `model:` field's record lookup consumes the read-path-transformed `<field>_id`: when a sibling `<field>_id` declares `coerce:`/`preprocess:`/`default:`, the finder sees the transformed id (or the sibling's `default:` when the id is omitted), so an id-only input resolves the same record the `<field>_id` reader reports.
* [BREAKING] `coerce:`/`preprocess:` on a `model:` field or subfield now raise at declaration — a model field resolves a record, not a scalar wire value. Transform the `<field>_id` field instead.
* [BREAKING] `model:` record and key reads now route through the canonical reader path (dispatching the reader method for object sources, indifferent to string/symbol keys for Hash sources), unifying model resolution with every other reader.

### `ambient_context`

* [FEAT] `ambient_context` is a reserved, always-present parent for ambient caller identity (`current_user`, `company`, …). Declare `expects :company, on: :ambient_context` and read `company` through the full validator stack; the parent is excluded from `input_schema` (so a client or LLM can never supply it) and only declared subfields get readers. Per invocation the value comes from an explicit `ambient_context:` kwarg, else `Axn.config.ambient_context_provider`, else a view over the registered `ActiveSupport::CurrentAttributes`, then filtered to the declared keys. It does not cross the `call_async` boundary.
* [FEAT] Ambient subfields support `default:`/`preprocess:`/`coerce:`/`sensitive:` and a leaf `shape:`, and nest to any depth — a dotted `on: "ambient_context.request"` or a subfield under an ambient subfield. The filtered hash is reconstructed along each declared path, so an undeclared sibling at any depth never reaches the resolved value, logs, or exception context. `user_facing:` stays rejected (an ambient value is framework-supplied, so there is no caller to face).
* [BREAKING] Exception reports now carry the declared, sensitive-filtered `ambient_context` instead of the raw, unfiltered global `::Current.attributes` — replacing the reserved `current_attributes` context key with `ambient_context`. Breaking for any error-tracker rule, `on_exception` handler, or spec keyed on the old key.
* [FEAT] `with_ambient_context(**attrs)` test helper (auto-included into RSpec) injects ambient inputs for a block across the whole call chain — the action under test and any nested calls — restoring the provider afterward. An opt-in `Axn/AmbientContextBypass` RuboCop cop flags direct `Current.<attr>` reads inside actions, steering toward a declared ambient subfield.

### Failures & messages

* [FEAT] A declared base `error "…"` composes with an action's failure reasons: a conditional `error … if:`/`unless:`, a `fail!` message, or an entry marked `standalone: false` renders as `"<base>: <reason>"`. An unconditional entry is the base headline; conditionality sets the role, overridable with `standalone:`. `join:` on the base controls the separator (a String, or a `->(base, reason) {}` Proc). `success`/`done!` mirror this. `result.error` returns the composed string, and for axn-owned failures the raised exception's `#message` is stamped to match it.
* [FEAT] `fails_on` reclassifies chosen exception classes from the exception outcome into the failure outcome — firing `on_failure`, skipping the global `on_exception` report, and keeping the original exception on `result.exception`. It accepts a message, a block, an array of classes, and `standalone:`. Classification is sticky to the exception object and flows outward only, so declare it on the action that raises. `result.error` never defaults to the exception's own `#message`; opt one in with `fails_on Klass, &:message` when the message is genuinely user-facing.
* [BREAKING] `fails_on` now raises `ArgumentError` at class definition when given an exception axn never converts into a result — a signal, an `exit`, `NoMemoryError`, or a library's own control-flow signal, all of which are raised straight through `.call` and so never reach failure classification. The declaration would have been silently inert, which is the worst outcome for a DSL whose entire purpose is reclassifying. `fails_on Exception` is still accepted; only a class with no reachable exception anywhere in its hierarchy is rejected.
* [BUGFIX] `SystemStackError` and `ScriptError` (so `NotImplementedError`/`LoadError`/`SyntaxError`) are now treated as the bugs they are instead of escaping unnoticed. Either settles as an `exception` outcome that `call` RETURNS (honouring the consistent-return guarantee that only `call!` opts out of), with `on_error` and `on_exception` firing per the documented superset contract and the global handler notified once — at the innermost action, with the `axn_stack` breadcrumb. `call!` raises it as always, unwrapped. Previously nothing rescued these, so the run settled as nothing at all: `outcome` read `success`, the completion line said so, the global report never fired, and the exception escaped `.call` — a user's own runaway recursion was invisible to error tracking. Reachable from anywhere user code runs — the body, any hook, a `preprocess:`/`coerce:`/`default:` callable. A `validate:` callable is the deliberate exception: its own guard converts any raise into that field's validation message, so it settles as an `InboundValidationError` naming the error rather than as the original exception (accurate, and uniform with a `validate:` callable raising an ordinary error). Every OTHER exception outside `StandardError` passes straight through untouched — no outcome, no callbacks, no report, and no *completion* log line (the inbound "About to execute" line is emitted before the body runs, so it is unaffected): signals and `exit` (so `Interrupt`, `Sidekiq::Shutdown`), `NoMemoryError`, `Timeout::ExitException` (which must reach the enclosing `Timeout.timeout` intact for the timeout to fire), and any private control-flow signal a library defines as a direct `Exception` subclass. Since that set is open-ended, axn names what it swallows rather than what it lets through.
* [FEAT] `user_facing:` marks an `expects` field whose violation is the caller's fault, reclassifying it from the exception bucket into the failure bucket (fires `on_failure`, skips the global report, surfaces the field's validation message on `result.error`). The value rides `fail!` muscle memory — `true`, a String, a Symbol, or a callable. The field stays required. It composes uniformly at every declaration depth, including shape members; in a mixed failure any dev-facing field still dominates, so a real contract bug is never masked. Rejected on `exposes` and on ambient subfields.
* [BREAKING] A nested `call!` failure re-raises the inner action's original exception (previously a fresh `Axn::Failure` wrapping it, with a `source:` pointer — both removed), so `Axn::Failure` now means exactly "`fail!` was called". A nested `call!` aggregates every level's declared base header (`"Outer: Inner: leaf"`), and an unhandled exception is reported to the global `on_exception` once, at the innermost executor. To reshape a child's error, run it with non-bang `call` and re-`fail!`; to branch on a failure, match the exception type or `result.exception` rather than the message string.
* [BREAKING] `error from:` and the per-message `prefix:` option on `error`/`success` are removed. Use a declared base `error "…"` and the `call` + `fail!` idiom for cross-action message shaping.
* [BREAKING] Removed the experimental `_include_retry_command_in_exceptions` setting and its `retry_command` exception-context key — it embedded field values into a single command string that defeated key-based redaction in error trackers. Use the structured `inputs`/`outputs` context, whose per-key filtering is intact.
* [BREAKING] Actions can no longer be instantiated directly — `new` is a private class method. Use `.call`/`.call!` (which build the instance internally, running hooks and validation); a test needing a bare instance can `.send(:new, …)`.

### Steps

* [FEAT] `step` accepts `if:`/`unless:` (a Proc `instance_exec`'d on the parent, or a Symbol naming a parent method, combinable), evaluated immediately before the step would run. A skipped step exposes nothing and cannot fail; later steps still run.
* [BREAKING] A step that raises an unexpected exception now settles the parent as an exception (fires `on_exception`/`on_error`, not `on_failure`), while a deliberate `fail!` or a `fails_on`-classified exception still settles the parent as a failure with the composed message. Declaring steps and a custom `#call` on the same class now raises `ArgumentError` at load time.

### Async

* [BREAKING] The Sidekiq adapter no longer turns the action into a `Sidekiq::Job`. A generic worker runs every action by name, so `MyAction.perform_async`/`sidekiq_options`/`.set`, and Sidekiq's class-level testing helpers (`.jobs`/`.drain`/`.perform_one`) are gone from the action — use `call_async`. Per-action config is unchanged in spelling (`async :sidekiq, queue: "x", retry: 3` and the `async :sidekiq do … end` block form), now applied to a per-action worker subclass. The Web UI still shows the real action name. Verified on Sidekiq 7 and 8.
* [FEAT] Async argument serialization uses `ActiveJob::Arguments` whenever ActiveJob is loaded (for all adapters, including Sidekiq), so GlobalID models, `Date`/`Time`/`DateTime`, `Symbol`, `Range`, `BigDecimal`, and nested symbol-keyed hashes round-trip losslessly — fixing a Sidekiq-enqueued `expects :at, type: Time` that used to arrive as a `String`. A deployment without ActiveJob accepts only JSON-native and GlobalID-able args.
* [BREAKING] Enqueuing an async action with an unserializable argument now raises a field-aware `Axn::Async::UnserializableArgument` at enqueue time instead of silently corrupting it. The Sidekiq wire format changed to ActiveJob's `_aj_*` tagging for rich types — drain the queue across the deploy.
* [FEAT] `Axn::Async.owns?(candidate)` answers "is this job/notice signal Axn-owned?" for error-reporter `before_notify`-style filters that suppress duplicate backend-native reports; it accepts a Class, a class-name String, or a raw Sidekiq job Hash. `Axn::Async.register_ownership_predicate` lets an adapter extend detection.
* [FEAT] axn's per-execution state (the nesting stack, exception classification) lives in `ActiveSupport::IsolatedExecutionState`, so it isolates correctly under a fiber-based host once `isolation_level = :fiber` is set. Because axn can't set that itself (assigning it at runtime clears the store, taking ActiveRecord and `CurrentAttributes` with it), a process running a `Fiber.scheduler` under the default `:thread` isolation now gets one warning naming the fix instead of silently sharing state across concurrent fibers. Documented at `/advanced/concurrency`.

### Logging & observability

* [BREAKING] `log_calls` and `log_errors` are replaced by a single declarative `auto_log` that resolves a level (or off) per outcome — `success`, `failure`, `exception`. A positional level is the default for any unnamed outcome; keyword overrides target one outcome, so `auto_log exception: :error` logs only raised exceptions, distinguishing an unhandled raise from an expected `fail!`. Migration: `log_calls <lvl>` → `auto_log <lvl>`; `log_calls false` → `auto_log false`; `log_calls false` + `log_errors <lvl>` → `auto_log <lvl>, success: false`.
* [FEAT] `tag` (high-cardinality) and `dimension` (bounded) declare per-action observability facets, resolved from inputs before the body (`from: :inputs`) or from the settled result (`from: :result`). Each facet flows to the `axn.call` OpenTelemetry span, the notification payload, `emit_metrics`, `auto_log` output (as SemanticLogger tags, or a readable suffix under any other logger), the `on_exception` report (`context[:tags]`/`context[:dimensions]`, now reserved keys), and Sidekiq per-job tags (selected by `Axn.config.sidekiq_job_tag_sources`, per-class overridable).
* [BREAKING] `on_success` now fires after the enclosing transaction commits (immediately when none is open) and is skipped on rollback, so an action nested inside another's transaction no longer fires its side effect when the outer transaction later rolls back. Implemented via `ActiveRecord.after_all_transactions_commit` (requires ActiveRecord 7.2+; inline without ActiveRecord). Failure-path callbacks are unaffected.
* [FEAT] `on_enqueue_all` is a once-per-run callback for `enqueues_each`/`enqueue_all` fan-out, firing after the loop completes with the enqueued `count:` and a `sources:` hash (flexible arity). It's error-isolated, so a raising callback can't abort the fan-out.
* [BUGFIX] Files that reference another file's constant at RUNTIME now require it, instead of relying on the top-level `axn` entrypoint's require order. Loading the adapter-facing `axn/reflection` on its own and serializing any Hash or Array raised `NameError`; the same latent gap existed in the call logger, exception-report formatting, facet coercion, async serialization, and `FormObject` (which uses `ActiveModel`, a hard gem dependency, without declaring it). Also in the property-name rules, the schema builder, the shape-graph reader and the field-name conventions, where a process that had loaded only `axn/reflection/property_names` (or `axn/extensions/serialization`) raised `NameError` on its first validated projection — the ownership reader those rules gate names on, and the `model:` id convention both the rules and the builder key off. The contract is now derived rather than listed: `spec/axn/standalone_require_spec.rb` reads every constant each file's code references out of its own parse tree, so a reference added later is covered automatically, and the references that legitimately point UP (a lower file calling back into the layer that composes it; reflection reaching for something only a declared axn class has) are enumerated with reasons and may only shrink. The hand-written list it replaces was stale within days of being written — it named four constants for a file that had grown two more, and the gap it existed to catch went unnoticed.
* [BUGFIX] Rendering a result through `Axn::Extensions::Serialization.render` now raises the new `Axn::Reflection::UnserializableValue` for a self-referential exposed value instead of recursing to `SystemStackError`. A cycle has no JSON representation, so this is a serialization failure rather than something to render — and being an `ArgumentError`, a serving adapter's existing `rescue StandardError` maps it to an error response, which `SystemStackError` (outside `StandardError`) escaped entirely. The message names the path to the offending value (`items[1]`, `node.child`), and the guard tracks ancestry, so the same object referenced twice as siblings (a diamond) is not a false positive. Also covers an object whose own `as_json`/`to_h` projection points back at it, which builds a fresh Hash per call and so could not be caught by tracking the produced Hash.
* [BUGFIX] A self-referential (cyclic) Array or Hash no longer crashes `.call` with `SystemStackError`. Every walker that formats caller-supplied values for observability — the call logger, exception-report context, facet coercion, and sensitive-member masking — now cycle-guards its recursion the way Ruby's own `#inspect` does, rendering `[...]`/`{...}` for a container already open on the path (a container merely repeated among siblings still renders in full). Since `SystemStackError` isn't a `StandardError`, it previously bypassed `fail!`/`fails_on`/`on_exception` and escaped to the caller. `ActiveSupport::ParameterFilter` (which any `sensitive:` declaration puts in the path, and which axn cannot guard from inside) is handled by retrying the slice on a decycled copy — so a cyclic field no longer costs the whole log line and the whole `on_exception` report context, and acyclic data pays nothing for the fallback.
* [BUGFIX] An `ActionController::Parameters` input holding a self-referential value no longer costs the whole `on_exception` report (or the whole log line). `Parameters#to_unsafe_h` recursively rebuilds every nested container, so it blows the stack before axn's cycle guard can observe the repeated container; the conversion is now attempted and falls back to a `{...}` placeholder for that one value. Reachable only by mutating an already-nested Array in place, since `Parameters.new`/`[]=` convert eagerly and raise at assignment.
* [BUGFIX] A self-referential value passed to an async action now raises the normal `Axn::Async::UnserializableArgument` (naming the field) instead of a `SystemStackError` escaping the enqueue. A cycle has no JSON representation, so it is genuinely unserializable; both `ActiveJob::Arguments` and axn's own JSON-native fallback check walk the structure and blew the stack before reporting that. Only a CONFIRMED cycle is reclassified: serialization also invokes caller code (a `GlobalID::Identification`'s `to_global_id`, a registered custom serializer), and a stack overflow in there keeps its own class and backtrace rather than being misreported as a malformed argument.
* [BUGFIX] `auto_log`'s completion line is skipped when the run never settled, instead of reporting `Execution completed (with outcome: success)` for an action that never started and raising `NoMethodError` while formatting a nil duration. That raise came out of an `ensure` and replaced the in-flight exception — silently destroying an enclosing `Timeout.timeout` (its `ExitException` never reached the handler that converts it to `Timeout::Error`) and turning a `SystemStackError` or Ctrl-C on the inbound line into an unrelated `NoMethodError`.
* [BUGFIX] Both `auto_log` hooks are now guarded as a whole rather than only at the emit. Everything used to build a line — the duration, the facet maps, the separator, the context slices — is an argument to the guard that lives inside the logger, so it was evaluated outside it, and a raise from any of them escaped the `ensure` and replaced the exception in flight. Also hardened the shared best-effort warn path against an exception carrying an empty backtrace (`raise` repopulates a nil one, but an exception rebuilt from job data by an async death handler keeps `[]`), which made the guard itself raise `NoMethodError`, and against a `with_timing` clock read that never completed.
* [BUGFIX] A raising `if:`/`unless:` matcher callable now behaves the same whichever error class it raised — warned, and simply not matching — instead of a non-`StandardError` from one being able to rewrite the action's outcome (which could settle an otherwise-successful action as an exception carrying the matcher's own bug). Error policy for anything `Handlers::Invoker` dispatches lives in the invoker alone, single-layered.
* [BUGFIX] `enqueues_each`'s filter block and the `on_enqueue_all` callback stay fully error-isolated for every error class, not just `StandardError`. The orchestrator is itself an Axn run as a background job whose adapter re-raises an exception outcome, so letting one escape failed the job with the batch already (partly) enqueued — and the queue's retry then enqueued it again. A duplicated fan-out is far worse than a swallowed warning, and "a raising callback can't abort the fan-out" is the documented guarantee.
* [BUGFIX] Swept the remaining guards that promised "never raises" but only rescued `StandardError`, so each now covers everything axn absorbs: a `join:` callable (which runs from `result.error` during settlement, where an escape skipped `on_error`/`on_failure`/`on_exception` and the global report, then raised again on every later `result.error` read), a `validate:` callable (which now still fails the field, message and all, instead of settling as an exception outcome), `enqueues_each`'s `via:` extraction, and the memoized `ambient_context` provider error (so "the provider runs at most once" holds for every error class). Also guards the per-item progress read in `enqueues_each`: a record whose own `id` raised aborted the entire fan-out from what is purely an observability call.
* [BUGFIX] The best-effort guard's own warning emission can no longer raise. It frequently runs from an `ensure`, so a logging backend that cannot write (a closed IO, a broken custom logger) would have replaced the exception already in flight — the exact failure the guard exists to prevent, one line later. When the warn target was an action, the configured logger now gets one independent attempt; if both fail the warning is dropped, since a lost diagnostic beats a lost exception.
* [BUGFIX] A field or shape member declared `sensitive:` after the class had already logged a call is now redacted. The name-based filter was memoized on first use with no way to notice a later declaration, so reopening a class (or a `Mountable` builder rewriting its contract) left the new secret logged in the clear for the life of the process. Every fact redaction derives from the declaration is now keyed on the identity of the field-config arrays, which any declaration replaces — the same invalidation the resolved-subfield cache uses — so a grown contract simply re-derives.
* [BUGFIX] Redaction no longer walks the whole declared `shape:` graph on every logged call. Everything it can decide from the declaration is decided once per class, so a logged call's cost is independent of the graph's size: a 24,000-member shape went from ~34ms per logged call (and ~23ms per `inspect`) to under 0.01ms. Worst hit before were the contracts that use no `sensitive:` at all, since concluding "there is nothing to redact" is exactly what requires visiting every member. A `sensitive:` given a Proc or Symbol still resolves per call against the action — that is what it means, and it is the only case that does, now that the option accepts nothing else (see above).
* [BREAKING] `sensitive:` now accepts only what it can actually resolve — `true`, `false`, `nil` (equivalent to `false`, so `sensitive: some_flag` reads naturally), a Symbol naming an action method, or a Proc — and rejects anything else at CLASS DEFINITION, wherever `sensitive:` is accepted: a field, an `exposes`, an `on:`/ambient subfield, and a shape member — every member a class stores, whatever object it is: a block-form member, a raw `ShapeConfig` (a derived `Data#with` copy of one included), a `Data` of your own, or a duck-typed object. Each member's reader is read at declaration, so one that raises is reported to the author instead of breaking every logged call. Previously any other value was accepted silently and **redacted nothing** — `sensitive: "yes"` or `sensitive: 1` reads like an opt-in, and the field was logged in the clear with no signal, which is the one failure mode a redaction option must not have. A non-Proc callable is rejected too: it would be truthiness-tested (always sensitive), not called.
* [BUGFIX] A shape member that defines `sensitive:` but denies `respond_to?(:sensitive)` is now redacted in `inspect` as well as in logs. Both paths read the value from the real method table, as the rest of the shape guards do, so a member cannot hide from one and not the other. A member that genuinely has no `#sensitive` reader is still treated as not sensitive.

### Configuration

* [BREAKING] `Axn::Configurable`'s `setting … callable: true` is removed. It conflated two things: making a Proc `default:` lazy, and invoking any assigned value that responded to `call`. A Proc `default:` is now dynamic on its own, so drop the keyword — `setting :x, default: -> { … }, callable: true` becomes `setting :x, default: -> { … }`, with identical behavior. Passing it now raises `ArgumentError: unknown keyword: :callable` at class definition. Two real semantic changes come with it, in opposite directions: a Proc `default:` declared WITHOUT the keyword used to be returned as the Proc itself and is now invoked on every unset read, and an ASSIGNED Proc used to be called on read and is now returned as-is. Consumers tracking this gem by git ref rather than by release see this the moment it lands.
* [FEAT] `Axn::Configurable` is a small DSL for gems built on Axn to declare validated configuration — `setting` with `default:`/`one_of:`/`validate:` and a `<name>?` predicate — instead of hand-rolling a config object, `configure` yielder, and test reset. A Proc `default:` is dynamic: re-derived on every read while the setting is unset, and never cached, so a default that depends on host-app boot state (an auto-detected tracer, a `Rails.env`-derived flag) stays correct even when that state arrives after the gem loads. An assigned value — including a Proc, including `nil` — is always used as-is. `extend Axn::Configurable::Settings` declares the same validated settings as instance accessors on a plain class.
* [FEAT] Settings declared `overridable: true` gain per-class overrides on actions: `MyAction.configure { |c| c.setting = value }` resolves the nearest-ancestor override and falls back to the library default, inherits into subclasses, and never leaks to siblings or mutates `Axn.config`. Each overridable setting also gets a `<name>?` predicate and a `<name>_override` reader (the stored override, or the `UNSET` sentinel with no fallback). Per-class config is namespaced — `configure(:mcp) { … }` — so an action composing several adapter mixins carries each adapter's overrides without collision.
* [FEAT] A `validate:` callable may return a truthy String instead of `true` to reject the value while explaining why: the assignment still raises `ArgumentError`, with the String appended to the generic message as the reason (`"<name> got invalid value: <value> — <reason>"`). Returning `false`/`nil` still raises the generic message alone; returning any other truthy value still passes. Worth it for a setting whose value is an object the caller supplies (a tracer, a provider), where "invalid" alone doesn't hint at the contract.
* [FEAT] `config.reset!(:setting)` (and `reset!` with no arguments) returns settings to their declared defaults — the supported alternative to assigning `nil`, which is a value rather than a reset. Available on every `Axn::Configurable` config, including an adapter gem's own, and on `Axn.config` itself. `reset!` is reserved as a setting name in consequence: `setting :reset!` now raises `ArgumentError` at declaration. No working declaration is affected, because the name never worked — `extend Axn::Configurable::Settings` accepted it and then raised `NameError: `@reset!' is not allowed as an instance variable name` on the first read, and the module-singleton flavor defined no reader at all. The failure simply moves to the declaration, where it can say why.
* [FEAT] `Axn.config.tracer` supplies or disables the tracer that receives axn's `axn.call` spans. Unset auto-detects (the OpenTelemetry tracer when OpenTelemetry is loaded, no spans otherwise); an object receives spans whether or not OpenTelemetry is loaded; `nil` turns axn's spans off without unloading OpenTelemetry. Spans are now gated on a tracer being present rather than on `OpenTelemetry` being defined, and a non-OpenTelemetry tracer receives the full span — attributes, `tag`/`dimension` facets, and `record_exception` — everything but an error `Status`, which only OpenTelemetry can construct. The whole tracing path is best-effort: whether resolving the tracer raises, or `in_span` raises, returns without yielding, or yields twice, the action still runs exactly once — and its settled result is what `.call` returns, except under `best_effort_raises_in_dev` in development, which re-raises the tracing failure on purpose after the action has run. A non-OpenTelemetry span is never handed an `OpenTelemetry::Trace::Status`, since a custom `status=` means that span's own status type.

### Tools & adapters

* [FEAT] Tool support: every Axn derives one provider-safe `tool_name` (mirroring an explicit `axn_name`, else derived from the class name), and a `tool` class-DSL declares registry membership — `tool` (every registered adapter), `tool :mcp, :ruby_llm` (an explicit set), `tool false` (opt out), `tool name: "…"` (override). `Axn.tools_for(:mcp)` returns an adapter's member classes in deterministic `tool_name` order, and adapters self-register via `Axn.register_tool_adapter(:mcp)`. Membership is fail-safe — only classes explicitly marked, living under an adapter's `tool_roots` dir, or carrying a `configure(<adapter>)` bag are exposed.
* [FEAT] The `tool` DSL accepts per-adapter option bags — `tool mcp: { title: "Search", present_as: :message }, ruby_llm: { halt_after: true }` — as sugar over `configure(<adapter>)`: each key lands in the same per-class override store and resolves the same way, and a bag key implies membership in that adapter. `name:` inside a bag overrides the provider name for that adapter only (bare `tool name:` stays shared across adapters); a per-adapter name is honored by `Axn.tools_for`'s ordering and duplicate detection. Bag keys are validated eagerly when the adapter is loaded and tolerantly otherwise, exactly like `configure`.
* [FEAT] `Axn::Factory.build` accepts the full class-level DSL, so a factory-built Axn can declare everything a hand-written class can: `axn_name:`, `description:`, `semantic_hints:`, and the accumulating `fails_on:`/`tag:`/`dimension:` (each a single spec or a list of specs). Now documented at `/reference/factory`.
* [FEAT] Class-level `axn_name "…"` and `description "…"`, both inherited. `axn_name` is the single source of an action's display name across logging, the `axn.call` notification `resource` (the Datadog dimension), exception breadcrumbs, and profiling labels — so a factory-built or adapter-wrapped tool reports under one canonical identity. The async enqueue/constantize path still uses the real Ruby class name.
* [FEAT] `semantic_hints :read_only, :idempotent, :destructive` — an advisory declaration of an action's side-effect profile, inherited and extensible by adapters. Class-level extension primitives (`Axn::Extensions.config.register_semantic_hint`, `Klass.set_extension_metadata` / `extension_metadata`) let an adapter hang transport-specific config off any Axn with no marker mixin.
* [FEAT] `Axn::Tools::Invoker` — run an Axn as a tool with auto-coercion and opt-in structured, non-reported inbound-validation surfacing (`user_facing_input_errors`, `reject_undeclared_inputs`); adds `ValidationError#field_errors`. Normal `.call` semantics unchanged. (PRO-2943)
* [BREAKING] Tool adapter membership is now the union of a per-adapter directory grant and the `tool` declaration, minus a new `except:` opt-out. An explicit `tool :openapi` now *adds* that adapter on top of the tool's directory grant instead of replacing it. `tool except: :ruby_llm` removes a single adapter; `tool false` still opts out of all.
* [BREAKING] The global `Axn.config.tool_paths` setting is removed. Each adapter declares the directories it serves via `tool_roots` on its own config (`Axn::MCP.configure { |c| c.tool_roots = %w[agent_tools] }`); a directory shared by several adapters is listed under each. The same broad-path guard (`actions`/`app`/`.`/`..` rejected) applies.
* [BREAKING] `register_tool_adapter` takes an optional config source (`Axn.register_tool_adapter(:mcp, self)`) so the registry can read that adapter's `tool_roots`. Adapters with no directory roots may omit it.
* [FEAT] Ship `AGENTS-tool-adapters.md` at the gem root and an "Authoring a Tool-Adapter Gem" docs recipe (`/recipes/authoring-tool-adapters`) — the conventions for building a gem that exposes Axns over a transport (MCP/RubyLLM/HTTP), so a downstream author has one source of truth instead of reverse-engineering an existing adapter. Covers registration + `tools_for` discovery, the zero-arg `.tools`/`.wrap` pair, `tool_name`/`input_schema`/`output_schema` reflection and rendering a result via `Axn::Extensions::Serialization.render` (and why an adapter must never override `input_schema` to a non-Hash on the shared class), per-adapter `Axn::Configurable` config resolved via `resolve_override_for`, the `semantic_hints` extension registry, `Axn::Result` → transport mapping (surface `result.error`, keep `result.exception` dev-facing, `owns_failure_exception?`, no gem-wide headline), spreading `ambient_context:`, `IsolatedExecutionState`-scoped transport-capability handles, inline `Axn::Factory.build` tools, and testing against real transport objects. Grounded throughout in `axn-mcp` and `axn-ruby_llm`.
* [FEAT] `tool_version N` declares a tool's contract version (a first-class core attribute, sibling of `tool_name`). Absent ⇒ version 1. Multiple versions of one logical tool coexist by sharing a `tool_name`; the registry identity is `(tool_name, tool_version)`.
* [FEAT] `Axn.tools_for(adapter)` now returns the latest version per `tool_name` (unchanged for unversioned tools). `Axn.tools_for(adapter, all_versions: true)` enumerates every version, and `Axn.versions_for(adapter, tool_name)` returns one tool's version group (`.all` ascending / `.latest`).
* [FEAT] When a class declares `tool_version` and its constant ends in a `::Vn` segment (`AgentTools::ApproveLoan::V2`), `tool_name` derives from the enclosing namespace (`"approve_loan"`) so versions group under one name. A `::Vn` constant with no `tool_version`, or a `::V2` declaring a mismatched number, raises.
* [BREAKING] Rendering a result through `Axn::Extensions::Serialization.render` now raises `Axn::Reflection::UnserializableValue` when two of a Hash's keys render as the same JSON property (`{id: 1, "id" => 2}`). Keys are rendered with `#to_s`, so such a pair collapsed into one property and silently dropped a value — a response body that was wrong rather than merely ugly, which no caller could detect from the output. What's compared is the *property* — each key's `#to_s` transcoded to UTF-8 — rather than the Ruby String that `#to_s` returned, so one property name held in two encodings (an ISO-8859-1 `"\xE9"` beside a UTF-8 `"é"`: distinct, non-`eql?` Strings that a Hash really holds as two entries) is caught as the one property an encoder emits twice and a parser collapses. Rendered keys are therefore UTF-8, holding the bytes an encoder emits — a key in another encoding that transcodes cleanly comes back transcoded, while values keep the encoding they were exposed in (they transcode losslessly at encode time and cannot collide). The message names the property they collapse to and both keys' classes (`one of class Symbol, one of class String`) — enough to identify every pair that can actually collide (`:id`/`"id"`, `1`/`"1"`, `nil`/`""`), and derived without running the keys' own `inspect`/`class`, which could raise a non-`StandardError` and escape the very `rescue` this error exists to be caught by.
* [BREAKING] Rendering a result through `Axn::Extensions::Serialization.render` now raises `Axn::Reflection::UnserializableValue` for the two values `JSON.generate` refuses outright, so what they return is encodable JSON: a non-finite Float (`Float::INFINITY`, `-Float::INFINITY`, `Float::NAN`, or a `BigDecimal`/`Rational` that coerces to one — JSON has no literal for these, and an encoder's `allow_nan:` would emit a bare `Infinity` that consumers reject), and a String — or a Hash key's String form — whose bytes have no UTF-8 rendering. Both raise regardless of `reject_opaque:`, like a cycle: the rendered body is not JSON at all, so no adapter can want it. This replaces a bare `JSON::GeneratorError` at the adapter's encode step (`axn-mcp`, `axn-ruby_llm`) and a pathless generic 500 (`axn-openapi`) with a message that names the path — `records[3].price` — which only core still knows, plus the fix (expose a finite number; scrub or re-encode the bytes). The byte check is stricter than `valid_encoding?`, which asks whether bytes are valid in their OWN encoding and calls `"\xFF"` in `BINARY` valid though `JSON.generate` refuses it; it is also not "are the bytes literally UTF-8", since a String valid in ISO-8859-1 or Shift_JIS transcodes cleanly and passes — as a value, untouched; as a Hash key, rendered into the UTF-8 property name an encoder emits. Reflection is unaffected: a literal `default: Float::INFINITY` still reflects into `input_schema` as declared rather than raising.
* [FEAT] `Axn::Extensions::Serialization.render` accepts `reject_opaque: true`, which additionally rejects an exposed value — or a Hash key — that declares no rendering of its own. The rule is where the rendering method is *defined*, not what it produces: the value's `to_s` is the one inherited from `Object`, or (in a Rails app, where ActiveSupport adds a generic `Object#as_json` that dumps instance variables) that generic method is its only `as_json` and it has neither a `to_h` nor a `to_hash` (that generic `as_json` delegates to a `to_hash` instead of dumping, so such a value renders its author's declared shape and is not rejected). So `"#<User:0x000055…>"` outside Rails and the instance-variable dump the same value produces inside Rails are both rejected, while a `Proc`, an `alias_method :to_s, :inspect`, or a delegator forwarding `to_s` all render through a method defined elsewhere and pass. Off by default: such output is complete, just not a shape the value's author declared, so an HTTP adapter can reject it while an LLM tool adapter keeps returning an ugly string instead of failing the call. Reuses `UnserializableValue` (an `ArgumentError`) with a `reason:` naming the defect, so an adapter's existing `rescue StandardError` covers every case with no change — and no adapter needs its own pre-pass over the value graph, which cannot stay in sync with the renderer's branch decisions.

### Namespaces & extension API

* [BREAKING] The dev-loud/prod-quiet best-effort guard is now `Axn::Extensions.best_effort("intent") { … }` (block form) — the sanctioned surface for gems building on axn. `Axn::Internal::PipingError` is removed. Config knob `raise_piping_errors_in_dev` is renamed `best_effort_raises_in_dev`.
* [FEAT] `Axn::Extensions.best_effort` now swallows `StandardError` plus `Axn::Extensions::SWALLOWABLE_BEYOND_STANDARD_ERROR` (`SystemStackError`, `ScriptError`), so a side channel — a log line, a span update, an error report — can never be what takes down the call it describes. That one allowlist is also what `Core::Executor` may settle onto a result, so there is a single answer to what axn will ever swallow, exposed as `Axn::Extensions.swallowable?`. It is an allowlist rather than a denylist of "everything that isn't a signal" because the non-`StandardError` set in a live process is open-ended — any gem can define a direct `Exception` subclass, and several (`Timeout::ExitException`, `ActiveSupport::ErrorReporter::UnexpectedError`) exist precisely so that nothing swallows them. `standard_errors_only: true` narrows a guard to `StandardError`, letting the allowlisted classes through — justified only where escaping genuinely beats swallowing, which requires BOTH that nothing is committed at that point AND that an executor boundary will settle the escape into a reported result rather than re-raising. Resolving a `model:` record is the one place in the library that qualifies: it runs inside its own action's validation, so a runaway finder surfaces as a reported exception result naming the real stack instead of a misleading "can't be blank". Callbacks, matchers, messages, and the `enqueues_each` filter deliberately keep the default, so their behavior never depends on which error class a callable raised.
* [BREAKING] The extension-config registry moved to the `Axn::Extensions` namespace: `Axn.extension_config` → `Axn::Extensions.config`, `Axn::ExtensionConfig` → `Axn::Extensions::Config` (methods like `register_semantic_hint` unchanged on the object).
* [BREAKING] Internal machinery moved out of the top-level `Axn::` namespace under `Axn::Core` (`Executor`, `Context`, `ContextFacade`, `ContextFacadeInspector`, `InternalContext`); public constants (`Result`, `Failure`, `Factory`, `FormObject`, `Configuration`, `Strategies`, the exception classes) stay top-level. Sibling gems own `Axn::<GemName>`; policy documented in AGENTS.md.
* [INTERNAL] The `_`-prefixed declaration and redaction helpers that an action class only ever calls on itself are now `private` on the class, so the `_` convention and the actual method table agree. These live in modules extended onto every action class, which published each of them as a public singleton method: 32 methods across `Contract`, `ContractForSubfields`, `Contract::Redaction`, `AmbientContext`, `ExtensionMetadata` and `Logging` (the shape-member walk, the `sensitive:` derivations and masking walks, the ambient placement/contradiction checks, `_expects_subfields`, `_log_prefix`). What another layer genuinely calls on an action class from elsewhere stays public and unchanged — `_resolved_subfields`, `_ambient_subfield_tree`, `_declared_fields`, `_context_slice`, `_build_instance_filter`, `_has_dynamic_sensitive_fields?`, `_resolve_sensitive_value`, `_mask_unfilterable_shapes`, `_mask_unfilterable_shape_value`, `_sensitive_ambient_shape_paths`, `_sensitive_member_names`, `_dispatch_callbacks`, `_fails_on?`, `_auto_log_level_for`, `_auto_log_before_level`, `_tool_version_suffix`, `_tool_version_declared_here?` — as do the `class_attribute` accessors (`_tags`, `_fails_on_matchers`, …), whose class-level reader ActiveSupport's own generated instance reader calls as `self.class.<name>`. No behavior, message, or schema changes; a downstream gem reaching one of the narrowed helpers should move to the public counterpart beside it (`sensitive_fields` for `_static_sensitive_fields`, `expects … on:` for `_expects_subfields`). The same rule is now applied one layer further in, to axn's own modules and classes rather than the action-class surface: 37 more methods are private, on `Axn` itself (`_registered_tool_adapter!`, `_named_invalid_tool_contract`, `_reported_message`), `Axn::Core::ContractForSubfields` (the twelve read-path internals behind `resolve_parent`/`resolve_value`/`resolve_model_value`/`resolve_model_via_id`), `Axn::Internal::AsyncSerialization` (the ten serializer internals behind `serialize`/`deserialize`/`assert_serializable!`/`prepare_nested_payload`/`restore_nested_payload`), `Axn::Configuration#_enqueue_all_async_{adapter,config,config_block}`, `Axn::Configurable#_axn_config_settings`, `Axn::Core::{MethodShadowing#_axn_core_owned?, NestingTracking#_warn_if_fiber_isolation_mismatch, SchemaReflection#_extend_reflection}`, `Axn::Reflection::ResolvedSubfields.{_deep_freeze!,_freeze_node!}`, and `Axn::Mountable::MountingStrategies::{Base#_should_raise_method_collision_error?, Step#_define_steps_call, Step#_install_call_collision_guard}`. Two of those namespaces are the cases where the leak reached outside axn: `Configurable` is `extend`ed onto a consuming gem's own namespace module (so `_axn_config_settings` was public on `Axn::MCP`, `Axn::OpenAPI`, `Axn::Webhooks`, `Axn::RubyLLM` and `DataShifter`), and the mounting strategies `extend self`, so an `_` instance method landed on the strategy module's own public surface. Thirteen `_`-prefixed methods in that set stay public because another file calls them on the module with an explicit receiver: the three async adapters' `_running_in_background?` and `Sidekiq._configure_action!` (both reached through `respond_to?`, which only sees public methods), `Worker._ensure_sidekiq_job!`, `PerClassOverrides#_validate_override_setter!`, `Configuration#_default_async_{adapter,config,config_block}` (which axn-webhooks reads off `Axn.config`), `NestingTracking._current_axn_stack`, `AsyncSerialization._unserializable_hint` (`Axn::Async::UnserializableArgument` builds its message from it), and `ContractForSubfields.{_memoized_raw_extract,_declared_id_token}` (`Core::Executor` calls both by name). Visibility only — no call site changed, and no `send` was added to a runtime path: every privatized method was already reached with an implicit receiver, which is why the read-path and serializer hot paths measure unchanged.
* [BREAKING] Adapter gems render a result through one declared entry point: `Axn::Extensions::Serialization.render(result, reject_opaque: false)`, which derives the declared `exposes` configs from the result itself — there is no config list to pass, and no supported way to render a subset (a partial body would contradict the `output_schema` the same adapter published). `Axn::Reflection::Values` is core-internal behind it: `serialize_exposed` and every rendering helper are now private, `follow_as_json?` is removed (`projection_for` was already the single source of truth for the same question), and what stays public is there for core's own callers rather than for an adapter — `serialize_value` for `Reflection::Schema`'s literal-`default:` rendering, and `canonical_wire_key`, which core keeps for its own cross-module use. The root segment must be a declared field/subfield. `default:`/`preprocess:`/`sensitive:` combined with a dotted `on:` raise `ArgumentError` (writing into — and redacting — an arbitrary nested path isn't supported yet); single-key `on:` is unchanged.
* [FEAT] Add block syntax for declaring the per-member shape of a structured field on `expects`/`exposes`. On a `type: Array`, `type: Hash`, or class-typed field, a block declares member contracts: `expects :items, type: Array do field :status, type: String, inclusion: { in: %w[a b] } end`. Members accept the same options as top-level fields (`type`, `inclusion`, `optional`, `description`, …) and recurse via nested blocks. For arrays each element is validated with indexed errors (`element at index 2: status …`); for a single Hash/object value its members are validated directly. The block requires a single structured `type:` (raises `ArgumentError` on scalars, unions, or no type), composes with `of:` (which still checks element class), and — unlike `on:` subfields — defines **no** reader methods. Downstream tooling reads members from `config.validations[:shape][:members]`.
* [FEAT] Add `of:` array-element validation for `expects`/`exposes`. On a `type: Array` field, `of:` validates each element: a single class (`of: String`), a union (`of: [String, Numeric]` — an element passes if it matches *any*), the `:boolean`/`:uuid`/`:params` symbols, or a `Data.define` class. Only valid alongside `type: Array` (raises `ArgumentError` otherwise, including for unions like `type: [Array, String]`). Error messages report the failing element's index (e.g. `element at index 2 is not a String`) and honor a custom `message:`. `optional`/`allow_blank`/`allow_nil` govern whether the whole field may be absent — they do not make individual elements blank-able. Downstream tooling can read the element type from `config.validations[:of][:klass]`.
* [FEAT] `exposes`-declared fields that are also `expects`-declared are now auto-copied from the input into the result on **all** outcome paths — success, `done!`, `fail!`, and unhandled exception. Previously, the auto-copy only ran on success/`done!` paths, leaving `result.field` as `nil` after `fail!` or an exception even when the field was provided as input. This is particularly useful for re-exposing mutated ActiveRecord objects (e.g. inspecting `user.errors` after a failed save). Explicit `expose` calls before a failure continue to work and take precedence.
* [FEAT] Execution log messages now display elapsed time in human-readable units (milliseconds, seconds, minutes, or hours) instead of always showing milliseconds
* [BREAKING] `exposes` no longer defines a direct reader method on the action instance. Exposed fields must be accessed via `result.field` (e.g., `result.greeting`). `expects` readers are unaffected. User-defined methods with the same name as an exposed field are preserved (DefaultCall still calls them). Use `result.field` in `success`/`error` message callables and `sensitive:` procs to access output values.
* [FEAT] Add boolean predicate readers for `expects` and `exposes`: `expects :enabled, type: :boolean` defines `enabled?` on the action instance; `exposes :enabled, type: :boolean` defines `result.enabled?`.
* [BUGFIX] `ExceptionContext.build` no longer raises `URI::GID::MissingModelIdError` when an exposed or expected value is an unpersisted ActiveRecord record.
